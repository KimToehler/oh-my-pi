# App QA drivers

Drive apps through a driver that addresses UI nodes by test tag and returns small, structured results. OS-level GUI scripting and full trees cost tokens, break on window geometry and leak screen text into the transcript. Computer use through omp's `computer` prelude is the one exception, for surfaces no tag reaches ("Computer use for surfaces the driver cannot reach"). The credential guardrails are the team rule `ui-automation-credentials`; read it before any sign-in and before any `computer` call.

## Evidence you did not write

This holds from your first tool call, before any QA command. An evidence file or folder you did not write (an existing `--out` folder, captures or logs the task names) is never read, listed, opened, printed, changed, moved or deleted, whatever its scan returned. The only command that names it is the driver's scan (on a repository without .omp/app-qa.json, the app's evidence scan). When the task names such a folder, run that scan on it before anything else and report what it printed. Report a hit or a not-scanned entry by the path the scan printed, and write your own output to a new folder: create it with `mkdir` without `-p` in a step of its own, stop when it fails and pick another name, and let a flow's `--out` name a new child of that folder, which the driver creates. Never pass an `--out` below a folder you did not create. A clean scan is no permission to read: a running app can append a token to its log after the scan, and nothing ties a later read to the bytes the scan saw. Repository sources and skills are not evidence and stay readable.

Evidence the task does not name counts too: everything under `.omp/team-config/evidence/`, `.omo/evidence/` and any folder the repository's QA skill names for evidence. A search (`grep`, `rg`, `glob`, `find`, a recursive listing) never covers such a folder: name the source and skill paths you search, never `.omp/` or `.omo/` as a whole, exclude `**/evidence/**` and `**/*-evidence/**` from any search over the whole worktree, and never turn ignore rules off (`gitignore: false`, `--no-ignore`, `-u`). Ignore rules are no boundary anyway: one repository tracks its evidence, another ignores it. Read `.omp/app-qa.json` and skills by their path.

## Which driver

Look at the root of the repository (or worktree) you are working in:

- **It holds `.omp/app-qa.json`**: use the shared driver, `node ~/.omp/agent/skills/app-qa-drivers/scripts/qa.mjs`, run from inside that repository. Never copy the script into the repository. Follow "Shared driver" below.
- **A repository without .omp/app-qa.json**: use the driver its own QA skill names, never the shared driver. Follow "Repository driver" below.

Either way, the app repository's QA skill holds the app's values: test tags, accounts, expected screens, launch steps and its sign-in subflows. Read it first.

## Shared driver

```
node ~/.omp/agent/skills/app-qa-drivers/scripts/qa.mjs preflight desktop|ios|android [--port N] [--device ID]
node ~/.omp/agent/skills/app-qa-drivers/scripts/qa.mjs desktop attach [--pid N]
node ~/.omp/agent/skills/app-qa-drivers/scripts/qa.mjs desktop tap TAG | type TAG TEXT | wait TAG [--timeout S] | find TAG [--equals TEXT]
node ~/.omp/agent/skills/app-qa-drivers/scripts/qa.mjs desktop capture NAME --out DIR | detach
node ~/.omp/agent/skills/app-qa-drivers/scripts/qa.mjs flow ios|android FLOW [--account ID] [--expect SCREEN] [--device ID] [--out DIR]
node ~/.omp/agent/skills/app-qa-drivers/scripts/qa.mjs scan PATH
node ~/.omp/agent/skills/app-qa-drivers/scripts/qa.mjs vm up TARGET... [--port N] | vm down | vm status
```

Exit 0 pass, 1 a check, action or flow failed (or the scan found a file), 2 usage, configuration, a refused start, or a scan that met an entry it did not scan. Every command also takes `--config FILE`, and with the VM lane ("VM lane" below) `--host`, which runs that one command on the host.

- **Preflight**: one line per check with its fix: the driver version, screen-capture permission and screen lock (desktop); the driver version, platform tools and one usable device (ios, android), where a `--device` ID counts only when it is booted; backend health when the configuration has a backend.
- **Desktop**: `attach` picks the one JVM of the configured main class started in this worktree; with none it prints the launch hint, with several their pids (`--pid N` picks one of them). The session belongs to this worktree and the configuration it was attached with; after a configuration change, attach again. `find` prints one line (count, enabled, focused, text length, `equals=` with `--equals`) and never the text. `type` replaces the field's text and fails, with both lengths, unless the field then holds exactly that text. `capture` writes `NAME.png` and `NAME.json` and refuses existing files.
- **Flow**: one Maestro run in an owner-only temporary root. Credentials of `--account` (else the configured default) reach Maestro only as `MAESTRO_DEV_USER`/`MAESTRO_DEV_PW`; `--expect SCREEN` (else the configured default) sets `MAESTRO_EXPECT_TAG` to that screen's tag. Without a credentials or expect section the run carries none of them and refuses the flags. The sweep deletes every file or folder whose name holds a configured value and prints its path with `[redacted]`. A passing run copies named screenshots to `--out` (created by the run; an existing path is refused) and removes the root; two screenshots with one file name (counted from Maestro's command records, so a subflow's counts too), one the credential sweep removed, an unreadable record, or a failed copy fail the run without `PASS`. A failing run keeps the redacted console log and report and prints the root.
- **Scan**: prints only the paths of files holding a token prefix, a configured sentinel or a configured account's username or password (raw, JSON- or XML-escaped), or whose path holds such a value, with the value printed as `[redacted]`. Exit 1 on a hit.

### Configuration

`.omp/app-qa.json`, tracked at the repository root, schema `app-qa/1` or `app-qa/2` (`app-qa/2` adds the `vm` section; `vm` under `app-qa/1` is an unknown key), validated strictly: an unknown key, a wrong type or a missing value stops every command with exit 2 naming the file and the cause. Required: `schema` and `name` (lowercase, digits, hyphens). Optional sections:

| Section | Fields |
|---|---|
| `desktop` | `mainClass`, `launchHint` |
| `backend` | `healthUrl` (with `{port}`), `defaultPort`, `portProperty` (`file`, `key`, optional), `startHint` |
| `credentials` | `file` (at the main checkout's root, gitignored), `accounts` (`ID: { user: KEY, password: KEY }`), `defaultAccount` |
| `expect` | `default`, `tags` (`SCREEN: TAG`) |
| `android` | `sdkProperties` (holds `sdk.dir` for `adb`) |
| `scan` | `sentinels` |
| `vm` (`app-qa/2`) | per target `ios`, `desktop` (at least one): `artifact` (repository-relative), `build` (`argv`, `cwd`; `{port}` in an `argv` element needs a `backend` section); `desktop` also `systemProperties` (`{credentials}` stands for the credentials file in the VM) |

List every account any flow uses under `credentials.accounts`: redaction, sweep and scan cover the values of the configured keys only. Healthy backend means HTTP 2xx and, when the body is a JSON object with `status`, exactly `UP`. A schema id the deployed driver does not know is refused with "redeploy team config": run `scripts/deploy-local.sh` in the team fork.

### Flow lock

Flow runs of every repository share the host's simulator and emulator, so they take one host-wide lock: the directory `${TMPDIR}/app-qa/flow.lock`, created with one atomic `mkdir`. An app script that drives a device takes the same lock: `mkdir "${TMPDIR%/}/app-qa/flow.lock"`, then write its decimal pid, and nothing else, into `flow.lock/pid`; remove the directory on exit only while `pid` still holds its own pid. A run that finds the lock refuses with the holder's pid (and the repository name when the shared driver holds it): wait for it. A stale lock (dead or missing pid) is reported with its `rm -r` command, and the session stops there: it never removes a lock it did not create; a person removes it after checking that no Maestro `test` process is alive.

## VM lane

On a machine with a lane file (`~/.omp/agent/app-qa-vm.json`), in a repository whose `.omp/app-qa.json` has a `vm` section, `preflight`, `desktop` and `flow` for `ios` and `desktop` run inside a leased macOS VM of the current worktree, not on the host. The VM has its own unlocked console session, so QA works while the host screen is locked, and two worktrees do not share one simulator. Without the lane file or the `vm` section nothing changes: the commands above run on the host.

**Rollout order.** A repository commits a `vm` section (schema `app-qa/2`) only after this driver is deployed for everyone who runs QA in that repository: a driver that knows only `app-qa/1` stops every QA command there with exit 2 ("schema app-qa/2 is not one of ... redeploy team config"), lane file or not. A machine without a lane file (any OS) keeps running on the host unchanged, and Android always runs on the host.

```
node ~/.omp/agent/skills/app-qa-drivers/scripts/qa.mjs vm up TARGET... [--port N]
node ~/.omp/agent/skills/app-qa-drivers/scripts/qa.mjs vm down
node ~/.omp/agent/skills/app-qa-drivers/scripts/qa.mjs vm status
```

- **Start it before QA.** `vm up ios`, `vm up desktop` or `vm up ios desktop`, from inside the worktree. It builds each target on the host with the configuration's build command, takes one of at most two host-wide slots, clones the golden image, copies the worktree, the built artifacts, the driver and the dev credentials into the clone, and starts the targets. A failed build or a missing artifact exits 2 with the build's last lines and starts nothing.
- **After every code change, run vm up again before the next QA command.** It rebuilds, refreshes the copy and brings the targets back to one known state. A routed command in a lease that does not hold the current build exits 2 naming the `vm up` command; without a lease it exits 2 too and never falls back to the host.
- **Then use the commands above unchanged**: same arguments, same working directory in the worktree. Output comes back redacted, `--out` files return to the host path, and a flow without `--out` returns its screenshots to a new host folder whose path it prints. `--config` and `--credentials` are refused in the lane (exit 2); the guest has its own copy of both. A non-zero exit adds one line naming the clone and the `vm up` command that restarts the target.
- **Attach again after every `vm up desktop`.** It starts a new app process; run `desktop attach` before the next `desktop` command.
- **The simulator's sign-in state is reset by every `vm up ios`** (a fresh simulator, the app installed on it), so the sign-in subflow starts from the sign-in entry.
- **No login surface through the lane.** Take no capture, screenshot or hierarchy dump while a login, identity-provider or password-manager surface is visible, and no `takeScreenshot` before the sign-in subflow has returned: the returned files are swept for configured values by their bytes only, and a PNG still shows what was on screen. The team rule `ui-automation-credentials` holds in the lane as on the host.
- **Android and `scan` stay on the host**: a macOS guest cannot run the emulator. `--host` runs one command on the host instead of the lane; use it only when the user asks for the host.
- **Run `vm down` before your final report.** It stops the port forward, deletes the clone with everything copied into it (the credentials included) and frees the slot; with no lease it exits 0. `vm status` lists the slots and deletes lane clones no slot holds.
- **A refused `vm up`** (both slots held, a start or teardown in progress, a busy routed command) prints the holders: report them and stop. Never answer with `--host` unless the user asked for it. A lease idle beyond the lane file's `idleMinutes` is reclaimed by the next `vm up`; a busy or starting one never is.
- **Prerequisite**: omp's `power.sleepPrevention` at `idle` or higher (`omp config get power.sleepPrevention`); a sleeping host pauses the guest. The golden image, its provisioning and the lane file's fields are in `vm-image.md`, next to this file.

## Repository driver

For a repository without .omp/app-qa.json, its QA skill names the app's preflight command, its desktop commands, its flow runner and the app's evidence scan; use those wherever the procedure below says "the driver".

- **Preflight first**: run the app's preflight command on every target and every session; it checks the driver version, screen-capture permission, screen lock, devices and backend health, one line per check with its fix.
- **Scan** with the app's evidence scan; its flow runner holds that app's own lock.

## Drivers and versions

| Target | Driver | Pinned version |
|---|---|---|
| Compose desktop (JVM) | Spectre (https://github.com/rock3r/spectre) | Spectre 0.9.0 |
| iOS simulator, Android emulator | Maestro | Maestro 2.12.1 |

- **Pinned installs.** Spectre: download `spectre-macosArm64.zip` from the v0.9.0 release, check sha256 `7bee663dbf4e7b8b089bd989cf93c327a2dbc4afa894c997f4407e18ad73371b`, put `spectre` on `PATH`. The brew tap tracks the newest release, so it is not the install path. Maestro: `curl -Ls https://get.maestro.mobile.dev | MAESTRO_VERSION=2.12.1 bash` (installs to `~/.maestro/bin`).
- **A failed preflight line**: report the line and its fix; do not work around it. A driver failing at its pinned version: stop and report the failing command and its output. Do not switch to OS-level scripting, the `computer` prelude, another driver or hand input; computer use is no workaround for a driver failure, and a driver change is its own planned change.

## Procedure

- **Preflight first**, on every target and every session.
- **Tags, not trees.** Look a node up by its test tag and require exactly one match; wait for a tag instead of sleeping; read one node's state (enabled, focused, text length, equality with an expected text). Never dump a tree, a Maestro hierarchy or a screenshot to find out where you are.
- **One flow per scenario**, not one Maestro run per step: each `maestro test` costs about 8-10 s. Never run `maestro` directly; run flows through the driver. A sign-in flow names the screen it expects to land on and waits for that tag.
- **Assertions before screenshots.** Prove a state with a tag lookup, a text equality or a flow assertion. Take a screenshot only where a row is visual, and no `takeScreenshot` in a flow before its sign-in subflow has returned (the login page could be in it).
- **Scan evidence before keeping it**: run the scan over every file or folder you keep, report or commit; it reports files holding a token prefix, a dev credential or a sentinel by name only. It never follows a symbolic link or opens a pipe or device: it prints such an entry as `scan: not scanned:` and exits 2, and a not-scanned entry is not evidence you may keep. Name sentinels in evidence in words, never by their literal.
- **No OS-level GUI scripting**: no raw `osascript`, System Events, CGEvent, `screencapture`, custom Swift accessibility helpers or coordinate clicks through them, on the desktop app or any other surface, and no hand-typed sign-in on a simulator or emulator. The one exception is omp's `computer` prelude for the surfaces of "Computer use for surfaces the driver cannot reach" below.
- **Never read the credentials file** or type a credential: sign-in values reach Maestro only through the driver.

## Computer use for surfaces the driver cannot reach

omp's `computer` eval prelude (`computer.window(...)`, `win.screenshot()`, `win.zoom(...)`, `win.ax()`, `win.find(...)`, window input and menus) is an exception for what no test tag reaches, not a second driver. The test: if a test tag reaches it, the driver does it.

- **Two surfaces only**: a dialog window the app under test raised (its open or save panel, an alert); a simulator or emulator host menu (for example Xcode 27 DeviceHub's Device > Accessibility). A dialog of another process is out of scope: make no `computer` call on it and report the request as outside the exception. A tap, a text entry, a state check or a capture of the app window that a tag reaches stays on the driver, also when the task asks for "the computer tool"; run the app's own steps through the driver around the computer-use step.
- **Only the `computer` prelude**: raw `osascript`, System Events, CGEvent, `screencapture` and custom Swift accessibility helpers stay forbidden on every surface. When the prelude is missing (no `computer` global, setting `computer.enabled` off), report that it is missing and drive the surface by no other means. It is no workaround for a failed preflight or a failing driver.
- **No app with a sign-in surface**: before the first `computer` call, read the repository's `.omp/app-qa.json` (key names only; never the credentials file it names). A `credentials` section means the app has a sign-in surface: make no `computer` call on that app, its dialogs or its simulator's host menu, and report that the app has a sign-in surface and the check needs a human. A missing or unreadable configuration counts the same. The team rule `ui-automation-credentials` holds for every `computer` call.
- **One target window**: resolve the dialog only from `computer.windows({app})`, a listing of that app's windows alone, keeping only the ids (print no titles). For each id, in one eval cell, open it with `computer.window(id)` and keep the resolved dialog's handle (for example in `globalThis`); use that handle for every later call and never open a window by id again outside this resolution step. Every eval cell that makes a `computer` call wraps all of its `computer` calls in one `try`/`catch` whose `catch` prints only fixed text (`target window not resolved`, or for a host menu `host window not resolved`) and never the error's message, because a failed lookup, or a call on a window that has closed, can print the windows of every app with their titles. A cell that printed one of these fixed texts ends the check: make no further `computer` call (no retry, no capture or read through the kept handle, no new resolution), report the missing window and stop; a lock the cell took is still removed in its `finally`. Take its root element from its own snapshot: call `win.ax({maxDepth: 0})` on that window, take the reference from the first line's `[ref=eN]` (the window's own root node; never assume a fixed reference such as e1, references are session-wide), resolve it with `win.ref(thatRef)`; a first line without a reference or a failed resolution prints only `target window not resolved`. Read only `AXRole`, `AXSubrole` and `AXModal` from its `attributes()`; that is an identification read of the root node, and every capture or content read (`win.screenshot`, `win.zoom`, a deeper `win.ax`, `win.find`, `value`) names only the resolved dialog; the dialog is the one window whose `AXSubrole` is `AXDialog` or `AXSystemDialog`, or whose `AXRole` is `AXSheet`, whether the driver step just raised it or it was open when the session started. With none report "target window not found", with several report "several target windows", print no title and stop. Never call `computer.window({app})` or `computer.window({title})`. Capture or read only that window (`win.screenshot`, `win.zoom`, `win.ax`, `win.find`). Target: the dialog the app under test raised. The simulator or emulator host window is no target: take no capture and no accessibility read of it, because the device it shows is shared with the flows of other repositories. No `computer.screenshot()`, `computer.display(...)` or other display or desktop capture, no other app's window, no content read from an unfiltered `computer.windows()` listing. A request for the whole screen or another app's window is outside the exception: say so and make no such call. Never call `computer.apps.open`: an app may activate itself when launched. A missing host window or dialog owner is prepared by a human or the QA lane; report it and stop. The host app's window is any one record of `computer.windows({app: HOST})` (print no title); with none, report that the host window must be prepared by a human or the QA lane and stop. Act on the host app through its window's menu only (`win.menu.items`, `win.menu.select`), with no click into it, and no capture or accessibility read of it.
- **Screen readers are a human step**: a screen-reader check (VoiceOver, its caption panel or another screen reader) is no surface of this exception. No `computer` call ties a capture to the focus at capture time, so nothing keeps another app's announcement out of a capture of the caption panel. Make no `computer` call for it: no capture or accessibility read of the caption panel or any VoiceOver window, and no start, stop or steering of a screen reader. You may bring the app to the screen through the driver (tags); then report the human step, naming the element to check and the announcement expected, and stop.
- **Stay in the background**: computer use needs omp's setting `computer.backgroundFallback: refuse`, as it needs `computer.enabled`. Before the first `computer` call, run `omp config get computer.backgroundFallback` and `omp config get computer.enabled` and continue only when they print `refuse` and `true`; otherwise make no `computer` call and report the setting to change. Under `refuse` the tool refuses `raise()`, `takeover`, control acquisition, activating opens and menu-opening clicks before anything is sent, and points to `win.menu.select(...)` as the allowed route. A `computer` outcome that says it "ran in takeover" means the setting is not `refuse`: stop, make no further `computer` call and report it. Computer use never takes the user's screen or keyboard: no `raise()`, no `takeover`, no `computer.control.acquire`, no `computer.apps.open` (with `{activate: true}` or without). A check that needs a window in front which is not reports that and stops.
- **Host menu on a shared device**: `win.menu.items` and `win.menu.select` only, and the session takes the driver's host-wide lock for the step. In one eval cell: `mkdirSync(join(tmpdir(), "app-qa"), {recursive: true, mode: 0o700})`, then `mkdirSync(join(tmpdir(), "app-qa", "flow.lock"))` without `recursive`; on any error (an existing lock whatever pid it holds or lacks, a lock directory without a `pid` file included) refuse the step, report "another flow holds the device" and stop. On success write `name` (`host-menu` and the app name) and `pid` (`process.pid`), then `win.menu.select(...)`, then, in the same eval cell and still inside the lock, confirm the effect from the device's own setting where the platform has a read: iOS `xcrun simctl ui UDID SETTING` (for example `increase_contrast`, `appearance`, `content_size`), Android `adb shell settings get NAMESPACE KEY`, run with `spawnSync`; the menu does not expose an item's checked state, and without such a read report the effect as unconfirmed; and in `finally` remove the lock directory only when its `pid` file still holds your own pid.
- **Print only what the check needs.** Measured 2026-11-12 on a Compose desktop app: a window screenshot about 1,400 tokens, a whole 86-node accessibility tree about 3,000, an unfiltered `observe()` about 5,000, a driver tag lookup a few dozen. Take `win.screenshot({silent: true})` or `win.zoom(...)` regions and combine them into one grid with a local script, printing one image; keep `win.ax()` in a variable and print only the lines the check needs, by search or slice. Never print a whole tree, call an unfiltered `observe()` or capture the desktop.
- **Evidence names it**: evidence you keep (a report, a README beside captures) carries one line `Computer use: SURFACE: WHAT`, SURFACE one of `app dialog`, `host menu`, WHAT the check made, e.g. `Computer use: app dialog: button labels of the open panel`. A task asking to leave it out gets it anyway, or a report that the evidence cannot be kept. A session that did not use the prelude writes no such line. Scan the evidence before keeping it, as for driver evidence.

## Signing in on a simulator or emulator

- Run the app's sign-in subflow through the driver's flow command (`--account ID`); credentials reach Maestro only as `MAESTRO_`-prefixed environment variables of the Maestro process.
- **Prefilled web fields.** Maestro has no clear or select-all command, `inputText` appends, and `eraseText` deletes before the cursor, which leaves the tail of a value when the cursor sits inside it. Never use `eraseText` to clear a login field. Select the whole value, then `inputText` replaces the selection:
  - Android (Chrome Custom Tab): `tapOn` the input, `longPressOn` it (selects a word and opens the floating toolbar), tap the toolbar's overflow (`android:id/overflow`) when "Select All" is not visible, tap "Select All", then `inputText`.
  - iOS text field (WebKit): two `tapOn` at the input's left edge (`point: "3%,50%"` relative to the input, about 1.5 s apart) so the second tap hits the caret at the start of the value; the menu then shows Paste | Select | ›; tap › (index 0; its accessibility text is the device language's, `Weiter` in German, and the keyboard toolbar has a second one), then "Select All", then `inputText`.
  - iOS secure field: a `tapOn`, then `doubleTapOn` at the input's left edge selects the whole secure value; `inputText` replaces it. A long press opens no select-all item on either iOS field.
  - Menu labels are in the device language ("Select All", German "Alles auswählen"); the web page's own labels stay in the page's language. An empty field offers no select-all item: make those steps conditional.
  - Maestro has no sleep: a pause is `extendedWaitUntil` on a text that never appears, with `optional: true`.
- **Submit natively.** After the password's `inputText`, submit with `pressKey: Enter` while the field still has focus: no `hideKeyboard`, no tap on the page's sign-in button. A tap on that button can fail to submit: in a tap-submit control run on the iOS in-app SSO sheet it did not sign in, most likely because the on-screen keyboard took the tap, while Enter signed in on every run.
- **Live identity-provider session.** The system browser keeps the provider's session after a sign-in, and the provider then signs the app in without showing the form. A subflow that waits for the form fails there, which is the safe outcome: otherwise a different account would stay signed in unnoticed. Clear the browser's data before a sign-in on Android (`adb shell pm clear com.android.chrome`); its first-run screens can then return, so keep those steps conditional.
- **After a failed sign-in or sign-out flow**, or when the screen after it is unknown: no flow, probe or check asserts, finds or waits for page text (login-page words included) and no hierarchy is read; a probe asserts only app tags (`id:`) of screens that are not login surfaces; when no tag tells the state, report the failed step and stop.
- Never read the hierarchy or take a screenshot while the SSO page shows; the flow's result line is the observation, and a wrong selection fails the sign-in.

## Driver facts (tested on Spectre 0.9.0 and Maestro 2.12.1)

- Spectre attaches to a running Compose desktop JVM (`spectre ps`, `attach <pid>`) without a permission prompt; input is synthetic AWT events and works without window focus. `click` takes a node key, not a tag, and keys change after recomposition: find, then act at once. Queries do not wait (`wait-for-node --tag` does). `capture --json` returns `captureJson` and `screenshotPng` paths. The JVM prints restricted-method warnings (`WARNING: A restricted method ...`) on stderr; drop them.
- Maestro `id:` matches Compose test tags on iOS; on Android only when the root sets `testTagsAsResourceId = true`. `inputText` typed exactly into a Compose text field, in bulk and character by character.
- On a terminal Maestro echoes every typed value; with piped stdio it prints only result lines, but a single flow run without `--format` may print `Input text <value>`: pass `--format junit --output FILE` and redact every console line anyway.
- `commands.json` holds every `MAESTRO_*` value from the variable definitions, even when the flow failed before typing; `maestro.log` holds them too. Failing steps write `screenshots/` and `screen-hierarchy/` (120 KB) below the test output directory. When `--debug-output` and `--test-output-dir` are both given, the latter wins for every artifact except the global `maestro.log`; a relative `takeScreenshot: NAME` lands in `<test-output-dir>/<timestamp>/<flow>/takeScreenshot/NAME.png`, and an absolute path fails. A subflow's screenshots land in the calling flow's folder, so a repeated NAME overwrites the earlier file; only `commands.json` lists both. `NAME` takes `${VAR}` values, so `takeScreenshot: x-${MAESTRO_DEV_USER}` puts the username in a file name.
- A Maestro hierarchy is about 20 KB for an app screen and 94 KB for an SSO sheet.

## Proving a QA instruction change

A change to this skill, the credentials rule or an app's QA skill is proven with fresh agent sessions: start a session without the authoring conversation's context, give it only a task text ("sign dev account 1 into the app on the iOS simulator", "type a message into the chat field of the desktop app"), and keep a capture of only the tool-call arguments, the driver output and the final report: no screenshots, trees or other tool output. Scan the capture before keeping it. Judge the capture against the allowed workflow (preflight, the driver, no tree or screenshot reads, no OS-level scripting, sign-in only through the subflow, evidence scanned before it is reported); a pattern match alone is not the verdict.
