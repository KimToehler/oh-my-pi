## Blockers

### Scope A (ReviewScopeA)

#### Finding 1

- **Area**: correctness and reasoning (CHECK 4, fail-open default on an incomplete round)
- **Defect**: When one reviewer of a `risky` round has no structured result after its retry, the whole round is discarded: no review.md is written or edited, even though the other reviewer delivered a REJECT with blockers. If a current OKAY record from an earlier round on the same digest exists (the plan's own "reviewed again unchanged" flow, and the migration case of re-reviewing an in-flight change), that OKAY stays current and `--reviewed` keeps authorizing apply over a rejecting verdict the review actually produced. The plan closed exactly this stale-approval route for the verifier path (TODO 5.3/5.5) and made it a criterion there, but its Incomplete-round requirement and Negative control lock the fail-open behaviour in for the reviewer path.
- **Evidence**: specs/openspec-plan-review/spec.md:274 "When a reviewer's retry also returns none, the round SHALL be incomplete: the agent writes and edits no `review.md` for it ... because the round has no verdict to record" — false in a risky round, where scope A's verdict exists; spec.md:293 Negative control forbids producing a record for that round; delivered instruction team-config/agent/skills/review-work/openspec/schemas/omp-gated/schema.yaml:417-419 "the round is incomplete: write no review.md and edit no existing one"; contrast spec.md:286-288 ("Failed triage supersedes an earlier approval ... the earlier OKAY is replaced by that round's REJECT record") and the requirement "A round is recorded before any fix or ask" (spec.md:~195, "leaves no earlier OKAY current"); the validator only judges the record it finds, so an untouched OKAY passes (team-config/agent/skills/review-work/scripts/validate-openspec-change.mjs:444-452).
- **Change**: Record the round whenever at least one reviewer delivered a verdict: write and commit review.md with Verdict REJECT, that reviewer's blockers (triaged, or Awaiting `triage` when triage could not run), the failed reviewer named as incomplete, then tell the user and stop. Keep the no-record path only for a round in which no reviewer delivered a verdict, and say there that an earlier OKAY stays current. Rewrite the `Incomplete round` requirement, its "Retry recovers the lens"/Negative-control scenarios and schema.yaml:417-419 accordingly.
- **Verifier**: confirmed, blocking true, protected false. The scenario is supported: spec.md:274 and schema.yaml:415-419 prohibit updating any review record after a reviewer exhausts its retry, even when the other risky-round reviewer has returned REJECT. An existing same-digest OKAY therefore survives and passes the record-based checks at validate-openspec-change.mjs:444-452. The failed-verifier protection in spec.md:286-288 does not cover this reviewer-failure branch. No named task exercises partial reviewer failure against a current approval; the instruction audit does not catch it because the negative control itself requires the no-record behavior. Ordinary task failure can therefore leave apply authorized despite a delivered rejection.

#### Finding 3

- **Area**: CHECK 8, no silent runtime fallback (pinned reviewer model)
- **Defect**: The pinned model is a runtime value that is silently substituted when the intended one fails, and nothing in the record shows it: (a) a subagent whose model has no working credentials falls back to the parent session's model — the Opus planner — with only a logger.warn; (b) the seed's model-keyed retry chain sends `onara/cx/gpt-6.1-sol` to `onara/cc/claude-opus-5` on any retryable error (`retry.fallbackOn: any`). For a `standard` change that is the only reviewer, so a whole round can run on the planner's own family while review.md records no model. The plan's answer to this trigger is factually wrong, and F1 only observes fixture runs.
- **Evidence**: design.md:83 "[Pinned model renamed by the router] → the task fails, the round is incomplete and the user is told; nothing passes silently" vs packages/coding-agent/src/config/model-resolver.ts:1746-1779 (auth fallback returns the parent's model, `authFallbackUsed: true`), packages/coding-agent/src/task/executor.ts:4680-4686 (only `logger.warn`), packages/coding-agent/src/sdk.ts:3221-3241 (same substitution on the deferred-pattern path); team-config/seed/config.yml:19-29 (`fallbackOn: any`; `onara/cx/gpt-6.1-sol: [onara/cc/claude-opus-5]`) with model-selector chain keys matching any session on that selector (packages/coding-agent/src/session/retry-fallback-chains.ts:368-369, :456-460); the record has no model field (team-config/agent/skills/review-work/openspec/schemas/omp-gated/templates/review.md:1-10), so spec.md:36 ("its run resolves to `onara/cx/gpt-6.1-sol:high`") is unobservable after the round.
- **Change**: Make the substitution visible in the record: add a resolved-model field per dispatch to templates/review.md and to step 7 of the review instruction (the task badge is enabled, team-config/seed/config.yml `task.showResolvedModelBadge: true`), require the round to be treated as incomplete (or recorded with that model and reported to the user) when a dispatch did not resolve to the pinned model, and rewrite design.md:83 to the real behaviour instead of "nothing passes silently".
- **Verifier**: confirmed, blocking true, protected true. model-resolver.ts:1746-1779 returns the authenticated parent model when the requested model lacks working credentials; executor.ts:4680-4686 merely logs that substitution. seed/config.yml:19-29 additionally configures retry fallback from sol to Opus. The review template at lines 3-10 records identities but no resolved model, and the dispatch instruction shown contains no enforcement against substitution. design.md:83's task-fails account does not describe the credential-fallback path. Task 4.1 checks child models in normal fixture sessions, but no task forces either fallback trigger, so those checks do not establish pinned-model behavior under the named ordinary runtime failures. The finding concerns a real credential/authentication path, hence protected is true, although the demonstrated consequence is reviewer-model substitution rather than credential disclosure.
