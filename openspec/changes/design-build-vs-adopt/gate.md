# Gate

- **Mandatory class**: none
- **Risk tier**: product
- **Author's risk assessment**: The change adds planning instruction text and one correctness-lens sentence; it changes no state machine, record, validator or script. It does send the planning session, which holds tools and the provider authentication, to read untrusted web content for every covered mechanism, so the instruction states that everything read during the search is data, never instructions (row A3 plants an embedded instruction, D5 checks the clause). Product tier because the lens sentence adds a blocking criterion to the plan review that gates product changes before apply. Too strict, a design spends one short subsection on a mechanism that did not need it, or the lens blocks a plan until the planner adds the decision. Too loose, plans stay as they are today. Neither weakens an existing review: the lens only gains a check. Class `none`: no auth, migration, wire or state behaviour is delivered, and no existing review-flow transition changes; the new criterion feeds the existing REJECT path. Revertible by reverting the text and re-deploying.
- **Whole-diff review**: not needed (one schema file, one template comment and one README paragraph, all model-read text; no independently testable module or runtime layer)
- **Accepted residual risks**: Whether a planner searches well, and whether the facts it records (versions, licences, maintenance) are true, stays a judgement the user sees in `design.md`; the lens checks from the plan only that the decision exists, carries the fields the form asks for and names its gaps. F1 shows the behaviour on fixtures, not a compliance rate. No real session meets a failing search provider: producing one needs a proxy or sandbox, which `Change verification` rules out, so the "Search provider fails" scenario is proven on the instruction text (D3) and on the lens's handling of an open Decision (C4) only; a planner that still records `none` after a real outage would surface as a build decision the user sees in `design.md`. The data clause lowers but does not remove prompt-injection risk from fetched pages: a model can still follow a well-crafted embedded instruction, as it can today whenever a session reads the web; F1 shows one planted instruction ignored, not resistance in general. If a future store-backed change makes the lens read the schema from the code repository instead of the planning home, the decision check is missing or stale for that plan: the plan gets the plan review it gets today, the omission is visible in the reviewer's output, and fixing the lookup is a text edit.
- **Out of scope for blocking**: plan-mode plans and the plan-mode `plan-reviewer` prompt; `web_search` for `plan-reviewer` or verification of cited facts by the reviewer; script or validator enforcement of the decision; the implementation phase; F1 proof of E3's schema lookup for a change that lives in a separate planning store, because no store is registered (`openspec store list`: "No stores registered"), `~/.config/openspec/config.json` sets no default store, and oh-my-pi, onara and weaver plan in their own repository, where every C row proves the lookup. E3 still names the planning home, so a later store setup reads the right schema.
