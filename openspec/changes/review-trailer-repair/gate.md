# Gate

- **Mandatory class**: concurrency-state
- **Risk tier**: product
- **Author's risk assessment**: The change touches the merge gate's review evidence, which is the audit trail that keeps unreviewed code out of `main` in every repository deploying team-config, so the tier is product. The worst realistic failure is fail-open: the repair path or the new checks accept a trailer whose verdict the reviewer did not reach. Examples: a repair turn flips a FAIL to PASS and is stored; `GC wave` records a PASS whose trailer the record check would reject; the shared module drops a rule the record check enforced before. Less severe is fail-closed: `GC wave` refusing a legitimate wave. That is recoverable, because nothing is appended and the command can be re-run. Class concurrency-state: the new trailer precondition decides whether `GC wave` may append the `gate_wave` event, which is a transition of the gate ledger's state machine; the record schema, the record check's rules, the ledger event shapes and the stop hook are unchanged.
- **Whole-diff review**: needed
- **Accepted residual risks**: A repaired trailer attests the form of a finished review, not a second review: its criteria and section list are written in a follow-up turn of the same reviewer session. A repaired FAIL artifact holds only the first line of each blocker, while the findings detail stays in the git-ignored original reply. The ledger does not store trailer digests, so the record may later cite trailer bytes other than those `GC wave` checked; the record check still validates whatever it cites. A wholly fabricated repair reply passes, as a fabricated trailer does today (the validator cannot witness a dispatch). The repair branch itself (missing or malformed trailer, then repair, then a fresh dispatch on failure) gets no deterministic live witness before merge (accepted by Tim, 2026-10-24, plan review round 3): a real reviewer does not reliably produce a broken trailer under the verbatim brief, and no harness exists for the skill's procedure. The F1 live probe s3 proves only that the reviewer is addressable, answers the repair with no tool call except the IRC reply (`write agent://` to the sender's id, the transport every messaged subagent answers through), and that its trailer validates with the original verdict. The order is checked as text by task 4.1, and the first real repair after the deploy is the post-merge witness. The Verify lines of tasks 6.2 (F3) and 6.3 (F1) check only markers (the report's first line, `RESULT: PASS` at the end of each scenario file); a hand-written file satisfies them (accepted by Tim, 2026-10-24, plan review round 12, choosing the option "Accept" with its stated reason): what binds them at F2 is limited: `validate-gate-record.mjs` binds the F3 report's bytes through `report_sha256` and admits it by its `.md` path, first line and location in a record whose `diff_base` and `reviewed_sha` must describe the code at HEAD, but it does not parse the report's content or range; for F1 it checks only that each `qa` row has `passed: true` and a non-empty `artifact` string, never that the artifact exists, is tracked, or matches a digest. The F1 evidence therefore rests on the F2 reviewers, who get the QA matrix and artifact paths in their brief, and on practice: this gate commits the four F1 scenario files with the record. No evidence verifier is added; the validator gap is a follow-up (Workflow follow-up in tasks.md). Corrected on 2026-10-25 after plan review round 15: the round-12 wording claimed the F1 artifacts must be tracked, which the validator does not enforce; Tim re-accepted on the corrected facts (option "Accept, corrected"). Whether a reply "states one verdict" before a repair (and so is repairable, rather than INCONCLUSIVE for zero or conflicting verdicts) is the orchestrator's reading of the reply, with no deterministic extraction rule, exactly as the verdict it passes to `GC wave --outcome` was read before this change (accepted by Tim, 2026-10-24, plan review round 14, choosing the option "Accept" with its stated reason): the `--verdict` binding catches a repair that changes the verdict, not a wrong first reading. F1 s3 runs the live `auditor` on the host runtime (the running omp `task` executor) with the host-installed `auditor` definition; this change touches neither (the definition is Out of scope for blocking), so s3 carries no runtime-file inventory and no control that swaps runtime inputs. From the worktree it takes only the brief, the `TRAILER REPAIR.` text and the validator, whose use its host-validator control proves. s3 witnesses addressability and the repair turn, nothing about the runtime (accepted by Tim, 2026-10-25, plan review round 16, choosing the option "Accept" with its stated reason).
- **Out of scope for blocking**: structured-output reviewer agents; the `auditor` and `oracle` agent definitions; the plan-reviewer paths (`review.md`, fix-delta `verdict.json`); the merge-gate stop hook; agent directories and projects (onara) that have not redeployed.
