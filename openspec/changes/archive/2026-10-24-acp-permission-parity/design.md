# Design

## Context

See proposal.md (Why). Current state, all paths under `packages/coding-agent/src/`:

- Every registry tool is wrapped by `ExtensionToolWrapper` (`sdk.ts:3601-3603`). Its `execute` (`extensibility/extensions/wrapper.ts:233-473`) is the TUI approval gate: `resolveApproval` (`tools/approval.ts:331-452`) → session approval check (`runner.hasSessionApproval`, `runner.ts:1073`) → `requestApproval(uiContext, …)` (`tools/approval.ts:699-738`), which uses `ui.approve` when the host has one and falls back to `ui.select`.
- ACP adds a second gate: a `Proxy` around `execute` (`session/session-tools.ts:891-1016`) for the names in `PERMISSION_REQUIRED_TOOLS` (`session/acp-permission-gate.ts:7-12`), with its own `allow_always`/`reject_always` map (`#acpPermissionDecisions`) and an `acpApprovedArgs` hand-off that tells the inner wrapper to skip its prompt (`wrapper.ts:361-364`). It is applied in five places (`session-tools.ts:468,605,660,1086,1101,1997`) and re-applied by `AgentSession.setClientBridge` (`agent-session.ts:7529-7531`).
- ACP's `ExtensionUIContext` (`modes/acp/acp-agent.ts:409-584`) has no `approve`; when the inner wrapper prompts (configured non-yolo modes) it falls back to a form elicitation, which silently denies on clients without `elicitation.form` (`acp-agent.ts:421`).
- The schema default of `tools.approvalMode` is `yolo` (`tools/settings.ts:313-317`). `protocolDefault` (`config/registry.ts:104-109`) can only pin the schema default, not a different value.
- Subagents get `tools.approvalMode: "yolo"` (`task/executor.ts:1216`), `hasUI: false` (`:4781`) and no client bridge; all spawn paths go through `runSubprocess` / `runSubagentFollowUpTurn` (task, `task/structured-subagent.ts:887` for eval `agent()`, `vibe/runtime.ts:1391-1392`, `task/workpool.ts:401`, `task/isolation-runner.ts:458`, `task/restore.ts:89`, `task/persisted-revive.ts:228`, revive at `executor.ts:4218`).
- `edit`'s `approval` returns the strictest write tier of its targets (`edit/index.ts:428-435`); `resolveApproval` already turns a tool decision with `override: true` into a per-call prompt outside yolo, ahead of user `allow` policies (`approval.ts:404-413`), and `sessionApprovalScope` refuses session scope for overrides (`approval.ts:461-468`).

## Goals / Non-Goals

**Goals:**
- One approval gate (the `ExtensionToolWrapper`) on every surface; ACP only provides the dialog.
- Close the two bypasses: unprompted exec-tier calls in default ACP sessions, and subagents ignoring a session-long rejection.
- Subagents of an ACP session see and write the editor's buffers.

**Non-Goals:**
- Forwarding subagent prompts to the client (decided against: the client knows none of the subagent's tool calls).
- Client terminals for subagents, subagent progress rendering in ACP (backlog P1 item, separate change).
- New TUI dialog choices: the TUI keeps its current answers; only ACP offers "always reject".
- Persisting session approvals or denials across sessions or restarts; `/forget-approvals` keeps clearing only remembered file/folder grants.
- Advisor tool sessions (`session-advisors.ts`); see gate.md.

## Decisions

### D1. Delete the ACP proxy gate; ACP implements `ExtensionUIContext.approve`
The ACP UI context gets an `approve(prompt)` that sends one `session/request_permission` through the record's existing permission requester (`surface.permissionRequest`, `acp-surface-v1.ts:270`, `acp-surface-v2.ts:525`, already wrapped in `trackInteraction`), and maps the selected option back to an `ExtensionApprovalAnswer`. Removed: `#wrapToolForAcpPermission`, `refreshAcpPermissionGates`, `clearAcpPermissionDecisions`, `#acpPermissionDecisions`, `#isExplicitAutoApproveMode`, `PERMISSION_REQUIRED_TOOLS`, `getPermissionIntent`, `PERMISSION_OPTIONS*`, `AgentToolContext.acpApprovedArgs` and its wrapper branch, and the two assignments of the ACP gate to `XdevState.decorateExecution` (`session/session-tools.ts:468,1997`). The generic `XdevState.decorateExecution` seam itself stays (`tools/xdev.ts:244-245,282,475`, covered by `test/write-xdev-dispatch.test.ts:217-229`); its doc comment drops the ACP example. `extractPermissionLocations` stays and moves next to the ACP approve implementation.
- Reaching `approve` without form elicitation. Two UI contexts matter. (1) The extension runner's: `#configureExtensions` passes the ACP UI context to `extensionRunner.initialize(..., uiContext, "rpc")` for every client (`acp-agent.ts:2697-2708`, `:2834-2835`), so `runner.hasUI()` (`runner.ts:1085-1087`, `:859-860`) is already true and the wrapper's no-UI rejection (`wrapper.ts:422-438`) does not fire; the wrapper calls `requestApproval(this.runner.getUIContext(), ...)` (`:440-450`), which reaches the new `approve`. (2) The tool context's: `record.setToolUIContext(uiContext, true)` runs only when the client supports form elicitation (`acp-agent.ts:2709-2710`), and the eval prelude approval check rejects when that context is missing or `hasUI === false` (`eval/preludes.ts:101-106`). Decision: install the tool UI context for every client as `setToolUIContext(uiContext, this.#supportsFormElicitation)`, keeping `hasUI` and the usage-fallback confirmer tied to form support (consumers such as `ask`, bash PTY selection and the computer supervisor keep their current behaviour), and change the prelude check to reject only when the context has no `approve` and `hasUI === false`. Rejected: passing `hasUI: true` for all clients, because that flips `ask`, PTY selection and computer control for clients that cannot answer forms.
- Why: a single resolver means ACP asks exactly when the TUI would (spec `acp-tool-permissions`), approvals stop depending on elicitation, and double prompting in configured non-yolo modes disappears.
- Alternative: widen `PERMISSION_REQUIRED_TOOLS` and call `resolveApproval` inside the proxy. Rejected: keeps two gates, two caches and the `acpApprovedArgs` hand-off, which is exactly the drift that produced this bug.

### D2. Approval prompts carry the call's identity
`ExtensionApprovalPrompt` (`extensibility/extensions/types.ts:261`) gains an optional `call: { toolCallId; toolName; args; tier; kind? }`, filled by `requestApproval` from a new `call` option. The wrapper passes its `toolCallId`, the tool name, `resolvedArgs` and `resolved.tier`; the eval prelude path (`eval/preludes.ts:108-110`) passes the enclosing eval call id when its context has one. The TUI dialog ignores the field. ACP builds `toolCall` from it: `toolCallId`, `title` (first line of `prompt.compact`), `kind: "execute"` for exec tier, `rawInput: args`, `locations` (see the next bullet), and for `bash` the `$ <command>` content row the proxy sent before. A prompt without `call` (e.g. an extension calling `requestApproval` directly) gets a fresh `toolCallId` so v1's required field is always set.
- Locations for `edit`: hashline and apply_patch payloads carry only `input` (`edit/schemas.ts:33-43`; hashline is the default, `edit/settings.ts:39-41`), so the generic extractor (`acp-permission-gate.ts:102-145`) finds no path. The `editInspect`-based parsing of `getEditDestructiveIntent` (`acp-permission-gate.ts:25-45`) moves next to the ACP approve as `editPermissionLocations(args)`, returning the path of every file op (and the move target) instead of only the first destructive one; ACP uses it for `edit` and `extractPermissionLocations` for every other tool.

### D3. Option mapping (spec: "Permission options mirror the TUI choices")
Option ids keep the four ids ACP clients already receive (`session/acp-permission-gate.ts:15-19`) for the choices that existed before, each equal to its kind: `allow_once` (this call), `allow_always` (this session), `reject_once` (deny), `reject_always` (deny for this session). Only the `always-ask-cached` grants, which have no legacy equivalent, get new ids: `grant:<scope>` and `grant:<scope>:always`, both of kind `allow_always`. `allow_always` is offered iff `prompt.session` is set, `reject_always` likewise (mode-raised prompt without cache targets). Answers: `allow_once` → `"once"`, `allow_always` → `"session"`, grants → `{ grant, always }`, `reject_once` → `"deny"`, `reject_always` → new answer `"deny-session"`. Unknown id → the approve throws a `ToolError` (call fails, not cancelled). `cancelled` outcome → `ToolAbortError`. Transport errors propagate (call fails). An aborted turn signal races the request as today (`untilAborted`).

### D4. Session denials live next to session approvals
`ExtensionRunner` gets `#sessionDenials` keyed exactly like `#sessionApprovals` (`${sessionId}\0${subject}\0${tier}`), plus `denySessionApproval(key)` and `isSessionDenied(subject, tier)`. The wrapper:
1. after `resolveApproval` on the effective args, computes the subject (`resolved.policyKey ?? tool.name`) and tier, and throws `denyError`-style `Tool call denied by user for this session: <subject>` when the subject+tier is denied in this session or an inherited ledger — before any prompt, regardless of `policy` (so a critical override cannot re-prompt; spec "Session-long rejection" negative control);
2. records the denial when `requestApproval` returns `"deny-session"`, then throws the deny. `requestApproval` today returns only `once`, `session` when offered, or an offered grant, and turns every other `approve` answer into `"deny"` (`tools/approval.ts:724-734`); it gains one branch that returns `"deny-session"` when the prompt offered a session scope (`session` set) and `"deny"` otherwise, so a host cannot record a session denial for a prompt that offers no session choice.
New/switched sessions start clean because the key embeds the session id (same as approvals). The TUI dialog never returns `"deny-session"`.
The wrapper is the only `requestApproval` consumer that offers a session scope (`wrapper.ts:445-450`); the eval prelude path passes no `sessionSubject` (`eval/preludes.ts:108-110`), so its ACP prompt carries no `reject_always` option (D3) and `requestApproval` can only return `"once"` or `"deny"` for it (step 2). Defence in depth: `approvePreludeInvocation` runs the prelude only on `"once"` and throws the deny error for any other answer, instead of rejecting only the literal `"deny"` (`eval/preludes.ts:111`).
- Alternative: a `tools.approval` deny written to settings. Rejected: persists beyond the session and edits user config.

### D5. Denial inheritance through a ledger chain
A small `ApprovalDenialLedger` object (in `tools/approval.ts`) holds `{ isDenied(subject, tier), parent?: ApprovalDenialLedger }`; the runner exposes its ledger, whose `isDenied` reads the live `#sessionDenials` for the current session id and then asks `parent`. `ExecutorOptions` gains `parentApprovalLedger`, taken at each spawn site from the parent `ToolSession` (new `ToolSession.getApprovalLedger?()`), copied into `SubagentSessionSpec`/`CreateAgentSessionOptions` (`approvalLedgerParent`) and handed to the child's runner. Because the parent link is live, denials recorded after the child started apply to its next call, and grandchildren chain through their parent. Revive paths (`executor.ts:4218`, `task/persisted-revive.ts`, `task/restore.ts`) take the ledger from the reviving parent session, never from persisted state.
- Why chain instead of snapshot: the spec requires denials recorded mid-run to apply.

### D6. Destructive edits are a tool-owned override
`edit`'s `approval` returns `{ tier, override: true, reason: "deletes <path>" | "moves <from> → <to>" }` when `fileOps` contains a `delete` or `move`, combined with the existing strictest-tier/deny logic (a tool `deny` from a read-only target still wins). `resolveApproval` already makes this a per-call prompt outside yolo, ignores it in yolo, lets a user `deny` win, and `sessionApprovalScope` already refuses session scope for overrides — so the prompt offers only once/deny on every surface (TUI included).

### D7. ACP default mode `write`, applied per session after project settings load
In `createAcpSessionFactory` (`main.ts:542-579`), right after `cloneForCwd(cwd)`: if `cfgToolsApprovalMode.isConfigured(nextSettings)` is false, apply `cfgToolsApprovalMode.override(nextSettings, "write")`. CLI `--approval-mode`/`--auto-approve` already override the base settings at `main.ts:1929-1936` before the factory runs, so they count as configured. Applying it per cloned settings (not on the base) keeps project config of each session's cwd authoritative.
- Alternative: extend `protocolDefault` with per-host values. Rejected for now: one setting needs it, and the registry change touches every protocol host.
- Verified: `cloneForCwd` carries the base settings' runtime overrides into the clone (`config/settings.ts:1309-1311`) and `isConfigured` covers env, runtime, overlay, project and global layers (`config/registry.ts:786-789`, `config/settings.ts:874-877`), so a CLI flag or `--config` overlay counts as configured on the clone.

### D8. Subagents of ACP sessions get a reduced client bridge
At spawn, when the parent `ToolSession.getClientBridge?.()` exists and the child is not isolated (child cwd equals the parent's cwd; isolated runs use their own workspace), the child session receives a derived `ClientBridge`: `readTextFile`/`writeTextFile` and their capability flags copied from the parent, `createTerminal`/`requestPermission` absent with capabilities false, `allowAgentInitiatedTurns: false`. Carried as `ExecutorOptions.parentClientBridge` → `CreateAgentSessionOptions.clientBridge` → `session.setClientBridge` during creation. With D1 removing the proxy gate, `setClientBridge` no longer re-wraps tools. Existing routing rules (`tools/acp-bridge.ts` `shouldRouteWriteThroughBridge`, `tools/read-summary.ts`) decide per path exactly as for the parent.

### D9. Why one change despite three subsystems
Approval core (D2, D4, D6), the ACP surface (D1, D3, D7) and the subagent executor (D5, D8) ship together: the denials D4 records exist only through the ACP option D3 adds and are only meaningful once D5 propagates them; under TUI semantics the spawn approval is the subagent boundary, which holds in ACP only once D1/D7 gate exec-tier spawn tools. D5 and D8 share one new seam (`ExecutorOptions` → `SubagentSessionSpec` → `CreateAgentSessionOptions` → revive spec), which is cut over once.

### D10. Steering supersede rides the shared approval path (main integration, 2026-10-24)
`main` added a user-steering supersede to the deleted proxy gate (`_session/steering`: a user steer sent while a permission request is open cancels it, withdraws the client's v1 dialog via `$/cancel_request`, and is delivered ahead of older queued steers). Merging `main` keeps D1 and moves that algorithm unchanged into `AgentSession.watchApprovalSupersede(loopSteeringSignal)`. `ExtensionToolWrapper` passes the call's loop steer signal (`ctx.toolCall.steeringSignal`) through `requestApproval` as `ExtensionUIDialogOptions.steeringSignal`; `createAcpApprove` opens one watch per request, races it against the client's answer, hands its signal to the requester (dialog withdrawal) and fails a superseded call with `Permission request superseded by user steering`. The proxy-only `SessionToolsHost` members (`steeringArrival*`, `waitForUser`) are removed.

## Risks / Trade-offs

- [ACP users with no configured mode now get prompts for `eval`, `task` and `browser` calls] → intended (spec); documented in `docs/approval-mode.md` and the changelog with the opt-out (`tools.approvalMode: yolo` or `--approval-mode yolo`). MCP tools stay unprompted in `write` because they are `write` tier (`mcp/tool-bridge.ts:728,866`), the same as in the TUI; changing their tier is out of scope (user decision, 2026-10-24).
- [Plain file edits no longer pass through any ACP prompt; before, ordinary edits were also unprompted, so no regression, but `write` mode makes it the documented default] → destructive operations keep a per-call prompt (D6).
- [TUI `write`/`always-ask` users now get a prompt for deletes/moves they did not get before] → changelog entry; `yolo` unaffected.
- [A subagent still running after its parent ACP session closed calls the client bridge] → the bridge request fails; a write fails with a `ToolError` (`tools/acp-bridge.ts:107-111`), and a read logs a warning and falls back to disk (`tools/read.ts:1574-1576`), the same as a parent-session read whose bridge call fails today. Accepted (gate.md); no new teardown code.
- [Permission request with a `toolCallId` the client never rendered (eval preludes, direct extension prompts)] → v2 carries `title` independently; v1 clients show the title from the `ToolCallUpdate`. Accepted (gate.md).
- [Removing `acpApprovedArgs`] → the arg-revision gap it covered disappears with the outer gate: the wrapper prompts on `effectiveParams`, i.e. the args that run.

## Migration Plan

Single cutover in one PR; no persisted data changes. Rollback = revert the PR. Users who want the old unprompted ACP behaviour set `tools.approvalMode: yolo` (then only user `prompt` policies and denials ask).
