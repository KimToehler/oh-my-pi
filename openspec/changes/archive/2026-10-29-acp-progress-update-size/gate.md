# Gate

- **Mandatory class**: wire-contract-api
- **Risk tier**: product
- **Author's risk assessment**: The change ships to every ACP user and changes ACP `session/update` frames on v1 and v2, which external clients (JetBrains Air, Zed, others) consume. In-progress `tool_call_update` frames lose `rawOutput`, and frames identical to the previous one for the same call are no longer sent. If D2 compared too little, a client would miss a real progress change (stale tool row) or a settled status (call shown as running). If D1 dropped `rawOutput` from a settling frame, a client would lose the tool result. Both are covered by exact-frame tests on v1 (golden fixture) and v2. The TUI, RPC and replay are unaffected. Class `wire-contract-api` because the frames are a supported contract read by independently released clients; tier `product` because every ACP user receives it.
- **Whole-diff review**: not needed (the change spans one module, the ACP mode in `packages/coding-agent/src/modes/acp/` — one mapper case in `acp-event-mapper.ts`, one handler in `acp-agent.ts`, one record field in `acp-surface.ts` — plus tests and one changelog line; the wire-contract class already runs both F2 reviewers)
- **Accepted residual risks**: A third-party ACP client that reads `rawOutput` from in-progress frames gets none; the end frame and a background job's final frame still carry it. An extension or MCP tool that reports edit-shaped details in progress frames loses the v2 diff on those frames (design D1). Map entries for calls that never end stay until the session record is disposed (design D2).
- **Out of scope for blocking**: Air's own journal and projection memory use (JetBrains code); existing oversized Air journals, which this change does not shrink; the task tool's 150 ms progress cadence and its details shape (the TUI consumes them); session replay, which sends only start and end frames; delivery of tool events after the prompt turn's foreground ended, for example ACP v2 background-job updates after `idle`: omp drops them today (`acp-agent.ts:2185-2191`) and this change leaves that unchanged; the requirements cover only frames omp sends (user decision 2026-10-29, round-3 review: "Die Anforderungen gelten für Frames, die omp tatsächlich sendet. Die Zustellung von Background-Updates nach dem Ende des Vordergrunds ist bestehendes Verhalten"); the upstream PR, held until the user decides
