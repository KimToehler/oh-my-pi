# Design

## Context

Canonical review instructions are static Markdown and YAML in `team-config/`, installed by the existing installer. The `omp-gated` schema's `review` artifact drives plan review; `review-work/SKILL.md` drives the F2 Phase 4 record, the fix waves and delta reviews; `integration-review/SKILL.md` Step 4 makes the F3 STOP and freeze decision. The schema already contains the seed of this change: it recommends Accept "when the fix would add a mechanism, procedure or check the proposal did not ask for". It is not reached early enough: the recommendation lives in step 6, after a third REJECT.

Measurement: `runs/gate-e2e-20261029/RESULT.md`, 22 changes, 711 reviewer invocations, 683 blockers classified. Plan review is 50% of reviewer service time; 29% of its rounds follow the last consumer-visible finding. Delta rejecting rounds are 23 of 52 process-internal, F3 8 of 23, F2 7 of 22.

## Goals / Non-Goals

**Goals:** fewer complete plan-review rounds without losing a blocking finding; one eligibility definition shared by the review instruction and every post-implementation lane; no new tooling.

**Non-Goals:** changing the blocking threshold, reviewer selection, lens count, F1/F3 ownership, gate records, validators or the ledger; any early-ask path in the post-implementation lanes; changing the between-waves exemption (the user removed it from this plan in round 4: today's text already exempts a comment "at your judgement", with "When in doubt, review", and the measurement showed no comment-reset problem); admitting the readable gate summary into the record (own plan); a delta path for commits after the final verdict (own plan); any numerical quality claim from the observational baseline.

## Decisions

### D0. One authoritative section

The definition lives once, in a `Blocker disposition` section of `review-work/SKILL.md`, next to the blocking threshold it negates. The schema's `review` instruction and `integration-review/SKILL.md` Step 4 reference it through the skill (`skill://review-work`). `packages/coding-agent/src/internal-urls/skill-protocol.ts` resolves that URL to the skill the session loaded, so it follows the active agent directory, whether that is the default, a profile or a custom `PI_CODING_AGENT_DIR`; a fixed `~/.omp/agent/...` path would read the default directory's copy in a profile session. When the section cannot be read, no blocker is eligible, which is today's behaviour. Both add only their own decision points; a restated copy would let a later edit leave the lanes deciding differently.

### D1. Eligibility is the negation of the existing threshold, not a second predicate

`review-work/SKILL.md:200` already defines what blocks: a realistic trigger whose result (a) breaks the goal, the value proof, a merge-gate criterion or an existing consumer, or (b) reaches a protected asset, a list that includes an audit trail. A blocker is Accept-eligible exactly when it misses both limbs and no exclusion applies. The exclusions name the classes whose immediate observer is misleading, in terms each lane actually has: security and privacy paths and protected assets; the audit trail, meaning the gate record, its trailers and the QA artifacts the validator binds (`validate-gate-record.mjs`), so a blocker about their binding is never "bookkeeping"; every blocker whose area names review_scope item 4 or CHECK 1 (plan review has no security lens; its checks lens carries item 4 next to the other mechanical checks, so the exclusion binds the label the reviewer writes in `area`, and a security defect under another label is still caught by "names a security or privacy path"); every blocker from a `security_delta: yes` trailer (F2); any change whose mandatory class is not `none`; and any blocker saying the change alters a review, gate or release mechanism so it would admit unreviewed or failing work. Precedence is one-directional: a label, lens or wording never makes a blocker eligible, an exclusion always makes it ineligible.

The value-proof limb keeps the threshold's meaning in every lane (user decision, round 6): a missing proof of any material behaviour or failure mode breaks the value proof, even when the criterion is partly proven, so such a blocker is never eligible. Only a gap in the form of evidence, meaning binding, wording or bookkeeping outside the audit trail, for a behaviour that stays proven by a check that can fail counts as weaker proof. This keeps the threshold unchanged at the cost of a less frequent early ask. A plan's own Verify is not a "gate mechanism"; that exclusion is about a change to the review tooling itself.

### D1b. Ambiguity blocks; an incomplete round keeps its stop

A blocker with no stated consequence, or an ambiguous or mixed one, is treated as blocking. A round in which a lens still returns no verdict after its retry is incomplete and keeps the existing behaviour (`schema.yaml:379-384`: no `review.md`, tell the user which lens failed, stop); it never counts as a clean round and never triggers an ask. This is the path by which a real defect would be lost, so every unclear state defaults against the ask.

### D2. Ask in the round, keep the old cap for defect-only rounds

A complete rejecting round that holds at least one Accept-eligible blocker is the point where at least part of the next round would re-examine process concerns rather than the product. The instruction asks the user in that round, per blocker: Accept recommended for each eligible one, only Fix or Stop for each non-eligible one, each with its stated consequence. The orchestrator then fixes the non-eligible blockers and those the user chose to fix, records each Accept in `gate.md` as today, and dispatches a fresh round. Every decision is recorded in that round, so no blocker waits in session state, an interrupted review loses nothing that is not already in the artifacts, and no OKAY round can stand on an unrecorded decision (user decision, round 6, replacing a carried-blocker list). A complete round with only non-eligible blockers is fixed without an ask, and the user is asked after the third REJECT as before, so this change cannot shorten a review that is still finding only blocking defects. The cost is possibly more asks per review. The measured tails (review-trailer-repair 17 rounds, m1-anthropic-body 10, gate-durable-qa-evidence 9) are exactly the case the earlier ask ends.

### D3. No unrequested mechanism for eligible blockers; real defects get their fix

The rule moves out of step 6 into the shared section. It binds only Accept-eligible blockers: answering one with a new script, procedure or check turns the checker into the next round's review target — this session's own `verify-f1.ts` cost two rounds while correctness had been OKAY since round 2. A blocker that is not eligible is fixed with whatever the correct fix needs, including a new check; the existing rule that a fix adding a subsystem becomes its own plan is untouched.

### D3b. Only plan review gets the early ask

F2, F3 and delta waves keep `CONTINUE`/`STOP`/freeze and their existing records: F2 records an unfixed blocker through `override` plus a `downgrades` entry (`below-threshold`, `accepted-residual`, `out-of-scope`, `frozen`); F3 records a freeze in its report's follow-up list with `GC decide --lane F3`; a delta acceptance is `GC accept`. F3 decides STOP and freeze in its own Step 4 before review-work's fix-wave step is reached, so `integration-review/SKILL.md` Step 4 references the section too.

### D5. Accept paths recommend; coverage is specific; the user keeps the final word

Every point where a blocker can stay unfixed applies eligibility: plan-review Accept and Override, the F2 Phase 4 override, F2 and F3 freeze, and delta accept. Plan review decides per blocker. A decision that leaves several blockers at once (an F2 override, a freeze, a delta accept) is recommended and offered only when every one of them is eligible or covered; otherwise the orchestrator offers fix, re-plan or stop and names each such blocker with its stated consequence. Under Risk tier `internal-tooling` at wave 3 or later, where `GC decide` already refuses continue, F2 and F3 offer re-plan or a re-tier, as today.

A blocker is covered only when an Accepted residual risks or Out of scope entry of the plan's reviewed merge-gate section (`gate.md` for an OpenSpec folder, `## Merge gate` for a `.omp/plans` plan) names the same defect class and consequence; a broad area list does not cover a specific blocker, and coverage never applies to an excluded blocker. `below-threshold` is used only for eligible blockers, `accepted-residual` and `out-of-scope` only for covered ones.

The user decided (round 2) that an explicit request to accept anyway stays possible rather than being forbidden, so no script changes: at plan-review Accept and Override, an F2 or F3 freeze and a delta accept, the request is recorded in the path's existing record with the user's reason in their words and the blocker's stated consequence. The user narrowed this in round 5: the ordinary F2 Phase 4 override, outside a STOP, never accepts a non-eligible, uncovered blocker, because none of the four `downgrades` rules the validator accepts would describe it truthfully; there the options are fix, another wave or re-plan. A hard refusal in `GC decide`/`GC accept`, or a new rule value, would need tooling changes and is its own plan if ever wanted.

### D4. Verify by replaying recorded rounds, not by asserting prose

No test asserts the new wording. Each edit task replays its own rows against the file it edited before it is ticked, and F1 re-runs all rows against the installed text at the final head. A row applies one instruction file to one recorded case from the measurement cohort, or to a case marked `constructed` where the cohort has none, and records the instruction sentence that decided it and the decision it produced. The 36 rows in `tasks.md` cover each requirement per lane: the exclusions and their precedence (item 4, CHECK 1 credential weaker proof, gate-record evidence, `security_delta: yes`, mandatory class, minor label on a consumer break) against an eligible CHECK 5 binding blocker outside the record; the value-proof reading (a materially unproven behaviour against an evidence-form gap); the ambiguity defaults; the mechanism rule; coverage (exact match, same class with another consequence, broad entry, broad entry with a security blocker); plan-review eligible, blocking, incomplete, mixed and mixed-third-REJECT rounds, the Accept effect and an insisted Override; the F2 eligible downgrade, an uncovered override, an insisted override that stays withheld, a withheld and an insisted freeze; a withheld and an insisted delta accept; an eligible, a withheld and an insisted F3 freeze; an unreadable section in plan review and at the F3 STOP; and a sandbox install whose installed and source hashes must equal the current source bytes. The Verify commands bind every row name to its edited file and expected decision, require a non-empty quoted sentence, check the evidence hash, and check the sentence against that file. The checker is an inline command per task, not a new script. The replays are the orchestrator's judgement; F2 reviews the instruction diffs against every negative control (accepted residual in `gate.md`).

## Risks / Trade-offs

- An early Accept can let a weak verification plan through → Accept is the user's decision, is recorded in `gate.md`, and the post-implementation gates (F2/F3/delta), which reject mostly on real defects, still run.
- Eligibility is a judgement → it is bound to the one existing threshold, defaults against the ask when unclear, and keeps Fix available at every ask; the measurement's own classification was a judge estimate and is cited as observational, not as proof.
- Fewer rounds could hide a regression in review quality → D4's replay keeps the defect case blocking; the next five gated changes are observed as workflow follow-up, as in the measurement report.
- More asks per review → each ask is per blocker and in the round it arises, so its cost is one question per eligible blocker; the alternative, a carried list, could lose a blocker across an interrupted session.
- A reference can be missed → both lanes reference the section through `skill://review-work`, which resolves from the active agent directory, an unreadable section leaves every blocker non-eligible, and the F1 rows for plan review and F3 cite sentences from their own files that name the section.

## Migration Plan

No state or schema migration. Edit the three instruction files in the task worktree; `scripts/deploy-local.sh` installs them into the default agent directory. Each profile (`~/.omp/profiles/*/agent`) or custom `PI_CODING_AGENT_DIR` root in use needs its own `env -u PI_PROFILE -u OMP_PROFILE PI_CODING_AGENT_DIR=DIR bun scripts/install-team-config.ts`, because a session reads the skill from its active agent directory. Projects that hold their own copy of the `omp-gated` schema are re-installed with `install-openspec-workflow.mjs`, because deployment alone leaves them on the old stopping rule; this repository's symlinked copy needs no step. Running sessions pick up the new text after a restart. Roll back by reverting the instruction commit, redeploying and re-running the project installer.
