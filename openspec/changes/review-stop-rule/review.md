## Blockers

### Correctness (StopCorrectness3)

1. **Design D1 / requirement "Security, gate and consumer blockers are never eligible" / task 1.1** — The exclusion "every blocker a security lens raises" has no referent in plan review, and the eligibility predicate overlaps the lens structure. The omp-gated review dispatches three lenses: correctness, verification, checks. The checks lens owns review_scope item 4 (security and privacy) together with CHECK 1-8 and the DOMAIN/PROCESS checks. So it is either (a) the security lens, which makes every checks-lens blocker ineligible, or (b) not a security lens, which leaves the exclusion with nothing to bind to. Option (a) removes the main source of the measured tail rounds. Option (b) lets a CHECK 1 holder/sink blocker be classed eligible by the consequence test alone, which only the scenario "Missing inventory on a credential path" prevents. A second overlap: the threshold's limb (a) already names "the value proof", so a verification-lens blocker that the plan's tests cannot catch a failure is not eligible. The same blocker can also be read as "a review, gate or release mechanism admitting failing work", which is excluded. The plan does not say which reading applies. The ambiguity default then makes such blockers block, so the early ask would rarely fire, or it fires inconsistently by orchestrator reading. Evidence: schema.yaml:334-340 (three lenses, named correctness/verification/checks) and :375-379 (checks lens carries security); tasks.md 1.1 "every blocker a security lens raises"; design.md D1; spec scenarios "Weaker proof of an unaffected path" vs "Review or release mechanism as the subject". No plan-review trailer carries `security_delta`; only F2 reviewers do (review-work/SKILL.md:223). Change: Define the exclusion in terms the plan-review round has. Name which lens and which check labels count as the security lens (e.g. CHECK 1 and the item 4 findings) and which do not. State that a verification gap in a plan's own Verify command is or is not a gate mechanism admitting failing work. Add replay rows for a CHECK 1 blocker and a CHECK 4/5 blocker so the rule is decidable.
2. **Requirement "Behaviour-neutral commits between waves" / task 1.2 (exemption allow-set)** — The rewritten allow-set removes an exemption that exists today and that no part of the plan mentions removing. Current text exempts "a final-verification checkbox, a comment, prose that no reviewer brief or criterion reads". The new rule exempts a commit only when every changed line is a comment or prose in a file that no "plan bundle" reads. A checkbox tick in `tasks.md` is a change in a plan-bundle file (the folder bound by `plan_sha256`), and the negative control says a plan artifact commit must be delta-reviewed. `plan-artifact-commit` → `delta-review` is also a row. After this change, every F1/F3 checkbox-tick commit needs a delta review again, because a commit with neither a delta verdict nor an exemption blocks the next wave. That reintroduces the waste the existing exemption was written to remove, and it works against the goal of fewer review rounds. Evidence: review-work/SKILL.md:432 ("a final-verification checkbox, a comment, prose that no reviewer brief or criterion reads … When in doubt, review"); :413 (a commit with neither a delta review nor an exemption blocks the next wave); gate-convergence.mjs:182-186 (an unreviewed commit has status "unreviewed"); tasks.md 1.2 and spec "Behaviour-neutral commits" Negative control. The proposal's changes list says the exemption becomes an allow-set, but never says the checkbox case is dropped. Change: Either keep the final-verification checkbox (and the tracked-checkbox tick the validator already permits after review) as an explicit allow-set member with its reason, and add a row for it. Or state in proposal, design and spec that the exemption is deliberately narrowed, with the cost accepted.
3. **Design D2/D3 and the plan-review round lifecycle (schema.yaml step 4 / step 6)** — A rejecting round that mixes eligible and non-eligible blockers has no defined handling for the eligible ones. Step 4 says "fix each blocker of every rejecting lens", and the plan keeps it. D3 forbids fixing an eligible blocker with an unrequested mechanism and routes it to "Accept, or its own plan". But the user is asked only at an all-eligible round or after the third REJECT. In rounds 1-2 of a mixed round the orchestrator therefore has no permitted action for an eligible blocker that needs a mechanism: it cannot fix it, cannot ask the user (the ask is withheld), and cannot ignore it (step 4 requires fixing). Whether the eligible blockers stay open and the next round re-raises them is left to nondeterministic fresh lenses. This also decides when the "first clean round" occurs, so the early-ask trigger depends on it. Evidence: schema.yaml:395-398 (step 4, "fix each blocker", cap after third REJECT); design.md D2 ("Rounds that still hold a non-eligible blocker keep the existing path") and D3; spec "Round with a blocking finding keeps the existing path" says only "a fix and a new round". Change: State the rule for eligible blockers inside a mixed round, for example: fix the non-eligible ones, carry the eligible ones as open without a mechanism fix, and ask at the first round where only eligible ones remain. Add a replay row (a mixed round before the third REJECT) with its expected decision.

### Verification (StopVerification3b)

1. **Quality and verification — tasks 1.1–1.3 and 2.1** — The Verify commands accept self-reported decisions without checking that the quoted instruction supports them or that the case was actually replayed. They accept any sentence from any of the three files, including one unrelated to the row; the artifact need only contain that sentence and the expected decision token. A broken or omitted rule can therefore pass every named row, including the negative controls, defeating the plan's value proof. The instruction edits are reversible, but an incorrectly accepted blocker can reach a release. Evidence: tasks.md:5 requires each case and deciding sentence to be recorded; tasks.md:9–11 and 17 check `x.observed===x.expected`, a hash, occurrence of `x.observed`, and occurrence of `x.sentence` in any file in `F`, but do not check the case, its source, the correct file for the row, or whether the sentence entails the decision. For example, `security-weaker-proof` can cite an unrelated existing sentence and record `fix-blocking` even if the security exclusion is absent. Change: Make each replay independently assess the actual case against the relevant complete instruction, capture the observed reasoning and decision, and include negative controls using deliberately broken instruction text that must fail. Bind each row to its designated file and case; retain the hash checks as evidence-integrity checks rather than treating them as behavioral proof.
2. **Quality and verification — F1 installation evidence** — The final Verify command does not compare installed bytes with source bytes or check replay sentences against the installed files. A failed, incomplete, or stale sandbox installation can still be marked `install-identical` and pass, so F1 cannot prove the shipped instructions are the ones reviewed. This is a reversible deployment defect, but it can leave the old stopping rule active in normal use. Evidence: tasks.md:17 requires a disposable installation and byte identity, but its command special-cases `sandbox-install` out of all file-content checks and only checks its self-reported `observed` token and artifact hash. For other rows `F` contains only `team-config/agent/...` source paths, not the disposable agent directory. The installer is a separate operation at scripts/install-team-config.ts:408–410. Change: Have the F1 probe capture and compare all three actual installed paths with their source bytes, fail on any missing or differing file, and run or validate the final replays against those installed paths. Record the command output and hashes as evidence.
3. **Quality and verification — scenario coverage** — Several required negative controls have no named replay that would detect their violation: post-implementation early-ask or wrong-record regressions, missing acceptance reason or consequence, and an exemption without a recorded reason. The listed positive examples do not exercise these broken states; an implementation with one of these omissions can satisfy every listed row while violating a specification criterion. Evidence: specs/openspec-plan-review/spec.md requires the post-implementation negative control under `Early ask stays inside plan review`; specs/review-blocker-disposition/spec.md requires negative controls under `The user's explicit acceptance is recorded` and `Behaviour-neutral commits between waves`. tasks.md:9–11 list positive `f2-eligible-blocker`, `delta-accept-insisted`, `f3-freeze-insisted`, and `comment-only-commit` rows, but no rows that remove a reason or consequence, introduce a post-implementation early ask or wrong record, or omit the exemption reason. Change: Add explicit replay cases for each broken state and require the review to reject the defective instruction; cover each affected lane and verify both the user's reason and the blocker's stated consequence in its actual record.

### Checks (StopChecks3)

1. **CHECK 6 — F2 Phase 4 override path** — The plan applies the new offer/recommendation rule at convergence STOP and delta acceptance, but does not apply it to the ordinary Phase 4 override and its accepted-residual and out-of-scope downgrade routes. Evidence: tasks.md:10 names only Fix waves steps 3 and 5d and ties only below-threshold to eligibility. The existing team-config/agent/skills/review-work/SKILL.md:351,357 permits a user-agreed override with accepted-residual or out-of-scope downgrades independently of convergence STOP. On an ordinary failing F2 wave, an orchestrator can therefore offer an override for a non-eligible security or consumer blocker, contrary to specs/review-blocker-disposition/spec.md:73-81. A resulting release defect may be irreversible. Change: Apply the eligibility and explicit-user-request rules to the Phase 4 override and every downgrade rule, and add a path-specific control for a non-eligible blocker covered by an accepted residual or out-of-scope entry.
2. **CHECK 7 — Eligibility definition** — The same eligibility decision is independently specified in the plan-review schema and review-work skill, without a shared consumed definition or a reason they cannot share one. Evidence: tasks.md:9-10 directs each file to state its own eligibility definition and exclusions; tasks.md:11 has F3 consume review-work's definition. design.md:9 makes a shared definition a goal, but D3b asserts consistency rather than providing a common artifact. A later policy update to one instruction can leave ordinary plan review and F2/F3 making different acceptance decisions, allowing a blocker to be recommended for acceptance in one lane when another forbids it; a released defect may be irreversible. Change: Make one shipped definition authoritative and have all three instruction entry paths explicitly consume it, or document why that cannot be done and provide a mechanism that prevents divergence.
