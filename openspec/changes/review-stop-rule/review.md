## Blockers

### Correctness (StopCorrectness4)

1. **Design D2 / openspec-plan-review spec 'Eligible blockers inside a mixed round' / task 1.2 (schema.yaml steps 4-5)** — The plan requires that eligible blockers be carried open 'in review.md' while the non-eligible ones are fixed and a new round runs, but the schema has no point at which review.md is written during that loop. Step 4 loops back to step 1 without writing review.md. Step 5 writes review.md once, after the last round. The 'carried' list therefore has no step that produces it, and the template, which the plan leaves unchanged, has no field for it. Fresh lenses in the next round also have no memory of what was carried. A lens can return OKAY without re-raising a carried blocker, and the round then closes with an open blocker silently dropped and no user decision. The ask fires only when the carried blockers are re-found, and nothing guarantees they are. The replay row `mixed-round-early` → `fix-and-carry` therefore tests a step the instruction cannot execute. Evidence: schema.yaml:395-401 (step 4: 'fix each blocker of every rejecting lens, then repeat from step 1 ... as a new round with three fresh lenses'), schema.yaml:402-408 (step 5 writes review.md from 'the last round's verdict'), templates/review.md (only Verdict/Reviewed digest/Reviewer/Round/Override/Blockers); validate-openspec-change.mjs:358-417 (review.md holds exactly one ## Blockers section, with the last round's blockers); specs/openspec-plan-review/spec.md:26-27; design.md D2. Change: Define where and when carried blockers are recorded. Either an explicit step that writes the carried list into the round's Blockers section, or a statement that the orchestrator keeps the carried list in its own state and prepends it to the next round's blocker set. Also say what happens when a later round returns OKAY while carried blockers exist (ask the user, or treat the round as not OKAY). Update the replay row to match.
2. **Requirement 'Ambiguity and incompleteness default to blocking' / spec 'Round with a blocking finding keeps the existing path' / task 1.2 row `incomplete-round`** — The plan handles a round in which a lens returned no verdict as 'blocking: fix the non-eligible blockers and run a new round'. The existing instruction already says what to do with such a round after the one retry. It is incomplete: write no review.md, edit no existing one, tell the user which lens failed, and stop. A round without a verdict has no blockers to fix, so the plan's disposition (`fix-blocking`, 'a new round') contradicts that stop rule while claiming to leave step 3 and the three-lens round unchanged. An implementer cannot satisfy both: either the new text overrides the stop, or the replay row's expected decision is wrong. Evidence: schema.yaml:379-384 ('If the retry also has no structured verdict, the round is incomplete: write no review.md ... tell the user which lens failed, and stop'); specs/openspec-plan-review/spec.md:20-22 ('including the ambiguous and incomplete-round cases ... THEN ... a fix of the non-eligible blockers and a new round'); tasks.md 1.2 `incomplete-round` → `fix-blocking`; design.md D1b. Change: For an incomplete round, keep the existing stop-and-tell-user behaviour. Restate the requirement as 'an incomplete round is never complete for the early ask and never counts as free of blocking findings'. Change the scenario and replay row to expect stop, or add an explicit decision value for it. Keep the 'fix and new round' wording for the ambiguous and no-stated-consequence blockers only.
3. **Requirement 'Behaviour-neutral commits between waves' / design D6 / task 1.1 rows `comment-only-commit`, `generator-doc-comment-commit`** — The allow-set is stated at two different levels that contradict each other. The requirement, D6 and task 1.1 exempt a commit only when its lines are a comment or prose 'in a file that no reviewer brief, plan bundle, criterion, agent-loaded instruction, or build, lint, codegen or documentation generator reads'. Read literally at file level, no source file qualifies, because the build and the linter read every source file, so a comment-only commit in source is never exempt. The scenario 'Comment-only commit in unread source' and the proposal ('a comment or prose that no brief ... reads') require the opposite, with the test applied to the changed text. The F1 row `comment-only-commit` → `exempt` and `generator-doc-comment-commit` → `delta-review` cannot both follow from the stated sentence. The result is either a vacuous exemption (no gain over today's checkbox case, while the existing text at SKILL.md:432 already exempts 'a comment') or an exemption whose boundary depends on the orchestrator's reading. Evidence: specs/review-blocker-disposition/spec.md 'Behaviour-neutral commits between waves' requirement text (file-level 'in a file that no ... reads') versus its Scenario 'Comment-only commit in unread source' (text-level 'no brief, criterion, instruction or tool reads that text'); tasks.md 1.1; design.md D6; proposal.md:15 (text-level); review-work/SKILL.md:432. Change: Pick one level and state it identically in the requirement, D6, proposal and task 1.1. For example: 'every changed line is a comment or prose whose text is not consumed by a brief, plan bundle, criterion, agent-loaded instruction, or a build, lint, codegen or documentation generator (doc-comment extraction counts; ordinary compilation of the file does not)'.

### Checks (StopChecks4)

1. **CHECK 3 / CHECK 4 – eligibility predicate vs. protected-asset limb (design D1, specs/review-blocker-disposition/spec.md:27-30 and :61-64, task 1.1)** — The plan defines Accept-eligible as the exact negation of the blocking threshold, but its two eligible examples ("evidence bookkeeping", and a CHECK 5 "evidence file is not digest-bound" blocker) can reach an audit trail. The threshold's protected-asset list names "an audit trail", and the F2 gate record, its QA artifacts and trailers are that trail. The exclusions the plan enumerates (security paths, item 4/CHECK 1, `security_delta: yes`, mandatory class, review-mechanism-admits-failing-work) do not list audit trail or gate-record evidence. The plan gives no argument that the enumeration is complete, and no control over input classes outside the listed examples. The only discriminator is the author's "no criterion, consumer or protected asset in its path" clause. A blocker saying the gate record's evidence is not bound to the reviewed bytes is bookkeeping by wording and gets Accept recommended, although the threshold blocks it. Evidence: spec.md:29 and :63 declare bookkeeping and an undigested evidence file eligible. SKILL.md:200 defines "A protected asset is production data, a real credential, third-party personal data, tenant isolation, money, an audit trail, or irreversible state". validate-gate-record.mjs:411-418 shows QA artifacts and trailers are the digest-bound evidence the record relies on. The replay rows (`check5-evidence-binding` → ask-accept-recommended, `security-weaker-proof`) never use a blocker about gate-record evidence, so none can fail on this. Change: Add audit trail (gate record, trailers, QA artifacts the validator binds) to the never-eligible exclusions, or narrow the two scenarios to evidence outside the gate record. Add a replay row for a gate-record-evidence blocker that must resolve to fix-blocking.
2. **CHECK 4 / CHECK 6 – accept-path predicate "covered by an entry of gate.md" (proposal.md:13, design D5, spec "Every accept path recommends only eligible blockers", task 1.1)** — Every accept path (F2 override, freeze, delta accept) is offered when each unfixed blocker is "eligible OR covered by an entry of the plan-reviewed gate.md". "Covered" has no definition. Nothing says a gate.md entry must name the same risk, and nothing excludes the classes that are "never eligible, whatever the observer". A security, item-4, `security_delta: yes` or mandatory-class blocker can therefore be recommended for `accepted-residual` or `out-of-scope` through a broad gate.md entry, which defeats the never-eligible requirement. The spec's own negative controls ("recommends recording an excluded blocker as an accepted residual risk") contradict the "or covered" clause, and no row tests the covered-plus-excluded combination. Only `f2-override-uncovered` exists, and it covers the uncovered case. Evidence: spec.md (review-blocker-disposition) "Every accept path…": "eligible, or is covered by an entry of the plan-reviewed `gate.md`". Design D5: "`accepted-residual` and `out-of-scope` keep their meaning". SKILL.md:357 already lets `accepted-residual` apply "when the plan's Accepted residual risks covers it" without a coverage test. Task 1.1 rows have no covered-security case. This plan's own gate.md Out-of-scope entry is a broad class list, which shows how loose "covered" can be. Change: Define "covered" in one sentence: the entry names the same defect class and consequence as the blocker. Say that coverage never applies to a never-eligible class unless the user explicitly requests it, with reason and consequence recorded. Add a row for a security or mandatory-class blocker that a broad gate.md entry mentions, expected `ask-accept-withheld`.
3. **CHECK 4 – exemption predicate (proposal.md:15, design D6, spec "Behaviour-neutral commits between waves", task 1.1; SKILL.md:432, gate-convergence.mjs:461-470)** — The allow-set depends on "no brief, plan bundle, criterion, agent-loaded instruction or build, lint, codegen or doc generator reads" the changed text, and on "no compiler, linter or build directive". The plan gives no way to decide this: no required search for readers, and no default for the unknown, corrupt or partial case. The existing "When in doubt, review" sentence sits in the very paragraph task 1.1 rewrites, and the plan does not say it stays. The plan's own Context says the exemption currently competes with that sentence. A wrong exemption is final for the whole gate: `delta_exemption` decides the commit for F2 and F3 alike. `exempt` takes any string as the reason and the script checks nothing about the commit's content. A comment-only commit whose text a test, doc generator or prompt loader reads (for example a source-reading test) is then never reviewed. The listed controls cover only constructed obvious cases (instruction file, plan artifact, directive, generator doc comment). None covers a reader that is undetected or unknown. Evidence: SKILL.md:432: "at your judgement… When in doubt, review"; gate-convergence.mjs:461-470 appends `delta_exemption` with any `--reason`, and :185 treats an exemption as accepted for the whole gate; gate-convergence.test.mjs:185-203 shows the exemption is shared across lanes. Rows `comment-only-commit` → exempt versus `directive-comment-commit` / `generator-doc-comment-commit` → delta-review never exercise an unknown reader. The gate lists "a broken exemption boundary" as in scope. Change: State in the rewritten paragraph that the orchestrator exempts only after searching the repository for readers of the changed file. Say that an unverified, unknown or partly unclear reader means delta review (keep "When in doubt, review"). Require the `GC exempt` reason to name the readers searched. Add a row for a comment in a file whose reader cannot be established, expected `delta-review`.
