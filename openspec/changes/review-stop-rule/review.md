## Blockers

### Correctness (StopCorrectness6)

1. **Correctness — value-proof threshold** — The plan makes some findings that break the existing value proof eligible for acceptance while claiming not to change the blocking threshold. Evidence: design.md:11 makes changing the threshold a non-goal, but design.md:25 and specs/review-blocker-disposition/spec.md:25 classify a plan Verify gap as weaker proof unless it leaves a criterion wholly unproven. For example, a criterion covering both creation and deletion has a test only for creation: deletion can be broken without failing any planned check, yet the criterion is not wholly unproven. review-work/SKILL.md:200 expressly blocks a realistic failure that breaks the value proof. The new rule permits recommending acceptance of that blocker; a later defect could reach release, with potentially irreversible effects. Change: Apply the existing value-proof threshold to each material behavior and failure mode, rather than treating partial proof of a criterion as sufficient; reconcile the requirement and its examples with the stated no-threshold-change goal.
2. **Correctness — carried-blocker lifecycle** — A normal interrupted review can silently discard eligible blockers that were never presented to the user. Evidence: design.md:33 and specs/openspec-plan-review/spec.md:31-37 keep mixed-round eligible blockers only in the orchestrator's carried list and require an ask even if later reviewers return OKAY. design.md:60 acknowledges that the list is lost when the session is lost and that the next review starts without it. If the next fresh lenses do not rediscover the finding, the workflow writes an OKAY review without the promised decision. This breaks the stated goal of not losing a finding; the loss is reversible only if the finding is rediscovered. Change: Preserve unresolved carried blockers across interrupted reviews, or prevent a restarted review from completing until the prior mixed round's blockers have been recovered and disposed of.
3. **Correctness — carried blocker override** — Overriding carried blockers after an OKAY round is reported downstream as an ordinary OKAY, not as a user override. Evidence: specs/openspec-plan-review/spec.md:34-37 explicitly permits Override when the latest round is OKAY with carried blockers. The existing validator requires an OKAY review to have no blockers and returns `reviewed: OKAY in round ...` regardless of a populated Override field (team-config/agent/skills/review-work/scripts/validate-openspec-change.mjs:404-416,425-430). Thus a normal mixed-round sequence followed by a clean round can proceed with unresolved prior findings while consumers see a clean result, undermining the review record; the record can be corrected later but the misleading gate decision may already have been used. Change: Define a representation and downstream outcome that preserves the carried findings and reports the override as such, or disallow Override after an OKAY round and require a durable residual or a fix.

### Verification (StopVerification6)

1. **Verification — specific gate coverage** — No replay distinguishes a genuinely matching residual-risk entry from a broad or mismatched entry for a blocker that is not independently excluded. Consequently, the specific-coverage requirement can be broken without changing any planned replay outcome. In ordinary review, that could cause an uncovered blocker to be offered for override; the instruction change is reversible, but a defect admitted to a release need not be. Evidence: specs/review-blocker-disposition/spec.md:113-124 requires the same defect class and consequence and makes a mismatch a negative control. The only coverage-specific row in tasks.md:9 is `covered-security-broad-entry`; its blocker is independently excluded because it names a security path. It therefore produces `ask-accept-withheld` even if the coverage rule incorrectly treats any broad entry as a match. Task 2.1 at tasks.md:17 repeats that same matrix. Change: Add replay cases for a non-excluded blocker with a truly matching entry, an entry naming the class but a different consequence, and a broad or different-class entry. Require only the exact match to count as covered, and include the cases in F1.
2. **Verification — shared-definition unavailable** — The requirement that both consuming lanes fail closed when the shared definition cannot be read has no replay case. A schema or F3 instruction that recommends acceptance when skill resolution fails can still satisfy the listed lane-specific replay outcomes, which all assume a readable definition. A missing or unavailable active skill can therefore lead to an unsupported acceptance recommendation. Evidence: specs/review-blocker-disposition/spec.md:9-13 requires both consumers to treat every blocker as ineligible when the section cannot be read. Tasks 1.2 and 1.3 at tasks.md:10-11 list normal round and freeze cases but no unreadable-section case; F1 at tasks.md:17 reruns only those rows and checks a successful sandbox install. Change: Add a constructed unreadable-section replay for each consumer, requiring acceptance or freeze to be withheld, and include both in the final installed-text QA.

### Checks (StopChecks6)

1. **CHECK 4 — carried-blocker completeness** — A restarted review can treat a lossy set of blockers as complete and silently pass without the required user decision. Evidence: design.md:31 carries eligible blockers only in the orchestrator’s list and requires an ask even after a later OKAY; design.md:57 acknowledges that the list is lost if the session is lost and the next review starts without it. specs/openspec-plan-review/spec.md:32-36 requires that a carried blocker never be dropped silently. For example, a mixed round carries a finding, the session ends before the next round, and fresh lenses do not repeat that finding: the new round can produce OKAY without asking or recording it. The lost review finding and resulting approval are reversible only by reopening the review. Change: Make pending carried findings recoverable across an interrupted review, or require a restart to detect the incomplete prior review and stop until those findings are resolved; add a restart-and-non-repetition negative control.
