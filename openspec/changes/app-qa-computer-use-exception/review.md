## Blockers

### Scope A (ComputerUsePlanReviewR22A)

1. **CHECK 1 — Window-resolution error sink**
   - defect: An ordinary missing-window case can expose other applications' window titles despite following the prescribed app-scoped lookup. For example, VoiceOver is not running, or the dialog closes before resolution. The resulting diagnostic can put unrelated private document titles into the session transcript and retained error evidence. Transcript disclosure is irreversible; stopping after the error does not prevent it.
   - evidence: openspec/changes/app-qa-computer-use-exception/design.md:35 promises no content from an unfiltered window listing, while design.md:53 explicitly retains window-resolution error text. Task 1.8 (tasks.md:14) preserves the lookup instruction in team-config/agent/skills/app-qa-drivers/SKILL.md:96, which permits computer.window({app}). packages/coding-agent/src/tools/computer/worker.ts:1938 constructs a failed lookup's error using describeWindowMiss(windows, ...), passing the complete window list. packages/coding-agent/src/tools/computer/window-miss.ts:53,62 prints those windows' titles, including other applications.
   - change: Design the lookup failure path as part of the window boundary. Use app-filtered enumeration with explicit empty/ambiguous refusal, and catch any subsequent handle-resolution failure inside eval before its raw diagnostic reaches tool output; emit a fixed safe outcome instead. Include errors, temporary captures and session output in the holder/sink inventory, and plant unrelated-window title sentinels in the missing-window control.
   - triage: confirmed, blocking true, protected true: The prescribed lookup at team-config/agent/skills/app-qa-drivers/SKILL.md:96 permits computer.window({app}), and task 1.8 preserves it. worker.ts:1938 passes the complete window list to describeWindowMiss; window-miss.ts:45-65 groups that list across apps and prints titles. An ordinary absent or closed target therefore exposes unrelated titles despite app-scoped selection. design.md:53 explicitly retains error outcomes. This is a delivered privacy-boundary defect, not merely missing verification; stopping afterward cannot undo transcript disclosure. It can be fixed in the instructions without changing the out-of-scope prelude.

2. **CHECK 5 — Focus validation is not bound to caption capture**
   - defect: The prescribed pre-capture focus lookup is a check-then-use race. During normal use of the shared desktop, the user can switch to another application after focused:true is returned but before the caption-panel screenshot. VoiceOver can then announce that application's private content, which the compliant session captures and reads. The restriction to a credential-free app under test does not protect the other application's data. Disclosure becomes irreversible once the capture is inspected in the transcript.
   - evidence: openspec/changes/app-qa-computer-use-exception/design.md:83 and tasks.md:13 prescribe computer.windows({app}) reporting focused:true before a separate caption capture; tasks.md:14 retains that ordering. design.md:37 acknowledges that the caption panel announces whatever has focus. These operations are independent in packages/coding-agent/src/tools/computer/worker.ts:1904-1907 (window listing) and :634-649 (capture); the capture has no expected-focused-app guard. Even a silent capture is written to a temporary PNG at worker.ts:657-658.
   - change: Do not treat the earlier focus sample as establishing which application's announcement is captured. Define a guarded or genuinely isolated context that supplies this guarantee, or hand the shared-desktop caption read to a human when that guarantee is unavailable. Add a control that switches focus between the successful lookup and capture and requires no unrelated pixels or text to reach the session.
   - triage: confirmed, blocking true, protected true: design.md:83 and tasks.md:13-14 require a focused:true listing before a separate caption capture. worker.ts:634-649 captures the target without an expected-focused-app guard, and :657-658 writes the PNG even for a silent capture. Switching foreground apps between these operations can put another app's announcement into the inspected caption image. The gate accepts caption content only while the app under test is in front; it does not accept reading unrelated announcements after focus changes. Thus the race defeats the stated boundary rather than merely requesting stronger verification of an accepted residual.

3. **CHECK 4 / CHECK 5 — Shared-device lock admission**
   - defect: Checking whether another PID currently appears in flow.lock does not serialize a host-menu operation with driver flows. A normal flow can acquire the lock after the check and before menu selection, so the session changes the shared device while that flow holds the lock, violating the explicit negative control. There is also a legitimate partially initialized state in which the lock directory exists but its PID has not yet been written; the plan specifies no fail-closed treatment for it. Device settings are reversible, but concurrent flow results become unreliable.
   - evidence: openspec/changes/app-qa-computer-use-exception/design.md:107 and tasks.md:14 require only taking no host-menu step while the lock exists with another PID. specs/app-qa-driver/spec.md:125,136 makes an operation while another process holds the lock a failure. The real driver acquires the directory atomically at team-config/agent/skills/app-qa-drivers/scripts/qa.mjs:898-907, writing pid only after mkdir. qa.mjs:916-921 explicitly handles that starting-holder interval. Nothing in the planned host-menu path acquires or holds this same lock.
   - change: Make the host-menu sequence participate in the existing host-wide lock protocol: acquire it atomically, keep a live owner through selection and confirmation, and release only the owner's lock. Refuse occupied, unreadable and partially initialized locks rather than interpreting an absent PID as permission. Include a control where a flow attempts to start between menu admission and selection.
   - triage: confirmed, blocking true, protected false: design.md:107 and task 1.8(e) prohibit menu steps when flow.lock names another PID but provide no acquisition spanning admission through confirmation. qa.mjs:898-907 atomically creates the lock before writing its PID, and :916-921 explicitly accounts for that starting interval. A driver flow can acquire the lock after the session checks it but before menu selection, or the session can encounter the PID-less interval. The resulting host-menu operation violates specs/app-qa-driver/spec.md:136 and compromises ordinary concurrent QA. The planned already-held-lock control does not resolve this delivered synchronization defect.

4. **Correctness — Background host-launch guarantee**
   - defect: The plan authorizes launching or reopening a host app with computer.apps.open(ID) as a background-safe operation, but refuse only blocks explicit activating requests; it does not prevent the launched application from activating itself. A host that activates on launch can therefore take the user's foreground and keyboard while the session follows the instructions and receives no 'ran in takeover' outcome. This breaks the new background-only requirement. Foreground theft is transient, but keyboard input delivered during it cannot necessarily be undone.
   - evidence: openspec/changes/app-qa-computer-use-exception/design.md:84 calls computer.apps.open(ID) '(background)'; tasks.md:13 introduces this instruction, and tasks.md:14 preserves it while asserting that computer use never takes the user's screen or keyboard. The requirement is explicit at specs/app-qa-driver/spec.md:59. However, packages/coding-agent/src/prompts/tools/computer.md:53 states that an app may still activate itself. worker.ts:1843-1868 rejects activate:true/reveal:true and otherwise calls openApplication; it supplies no general self-activation prohibition for this launch.
   - change: Remove the unconditional background-safety claim for apps.open. Require the human or QA lane to prepare a missing host window, as already required for VoiceOver and foreground preparation, unless a specifically supported launch route can establish the background guarantee. Exercise the no-window host case with a fixture that activates itself on launch.
   - triage: confirmed, blocking true, protected false: design.md:84 calls apps.open(ID) background-safe; tasks 1.7(c) and 1.8 preserve the instruction for a missing host window. The actual documented contract at packages/coding-agent/src/prompts/tools/computer.md:53 expressly permits app self-activation. worker.ts:1843-1868 rejects explicitly activating options but otherwise calls openApplication, so refuse does not establish the unconditional background guarantee. A normally self-activating host launch can violate spec.md:59 without a takeover outcome. This finding concerns the instructions' authorized route, not a demand to alter the excluded prelude or settings.
