Why the blockers keep coming: the plan is much shallower than what it promises. The spec promises end-to-end sign-in (open the app, reach the order list), the token on every API request, and pre-request refresh. The design is one sentence that hands the whole flow to a new client. The tasks are two lines that create three classes in shared/auth/. The repository has only shared/http/Client.kt: no app entry point, no redirect handler, no build or test setup. Each round, the reviewers find the next missing layer: round 2 the refresh race; round 3 the app wiring, the Client.kt wiring, the OIDC trust boundaries, token storage and token destinations, fail-closed predicates, and test scaffolding. Fixing these one blocker at a time adds new design surface every round, and the next round reviews that new surface again.

Recommendation: Re-plan. Rewrite design.md to cover the OIDC trust boundaries, the credential holders and sinks, the trusted-origin bearer policy, the app and redirect integration (or name it as a prerequisite, since the repo has no app), and the build and test setup. Then rewrite tasks with named tests and the F1 scenarios. This deals with the cause and keeps the goal. Re-plan can also do the PROCESS 3 cut properly.

Split is possible but not recommended. You could keep sign-in, storage and bearer injection, and move token refresh to its own change (refresh depends on sign-in, not the other way round). Users would then have to sign in again when the access token expires, and the 'Token refresh' requirement leaves this change. The cause above stays in the retained scope, and that scope is still auth-secrets-pii.
