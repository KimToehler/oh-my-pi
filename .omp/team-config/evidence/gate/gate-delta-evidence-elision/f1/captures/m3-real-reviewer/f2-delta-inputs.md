# F2 fix-delta inputs, m5-app-design-workspace (verbatim)

## Plan invariants, verbatim from the change's gate.md (the change's Merge gate)

Feature-specific criteria: not in plan as a gate.md field; the criteria are the requirements and scenarios under openspec/changes/m5-app-design-workspace/specs/.

- **Accepted residual risks**:
  - Visual and device QA runs on the desktop (macOS arm64), an Android emulator (API 36) and an iOS simulator only
    (FU-206); no hardware. Screen-reader behaviour is observed only by the means the QA driver permits (the desktop
    semantics dump, the accessibility trees, TalkBack speech where capturable), not by VoiceOver on macOS or iOS or by
    Accessibility Inspector: a human VoiceOver pass on macOS and iOS before any release is a follow-up recorded at merge.
    Accessibility of the page content is observed and recorded in F1, not a pass condition (design.md D-10).
  - The desktop engine is pinned and measured for macOS arm64 only; Windows, Linux and `macosx-amd64` show "not
    available on this device". Gatekeeper and notarisation of a distributed app, an org mirror and a signed installer
    stay with the desktop distribution (ADR-0038 open point 5, rest).
  - The size bounds and the CSP are the ADR's values, not yet checked against real design-skill output, which does not
    exist until a runner produces pages (design.md D-6).
  - The engine is stopped on every tab change and the page position is lost (design.md D-9).
  - `PreviewPane` and its width switcher have no shell caller until `m5-app-design-present` (design.md D-9).
  - One change holds two subsystems, the engine with its provisioning and proof, and the workspace around it; a
    defect in one holds the other back. They cannot ship separately (design.md D-0: one seam contract and one cutover).
  - An engine that cannot be brought to zero peer-to-peer traffic stops apply and amends the design (design.md D-8);
    the change has no disabled-engine path, so no engine that leaks ships, with the two Android windows of a later entry
    (agent under user policy 2026-10-24: a
    fail-closed evidence path for a case that may never occur is a mechanism the proposal did not ask for).
  - The Android WebView hands the app no request body, so on Android the blocked-request notice gives the count and the
    reason of CSP-refused requests and no host (design.md D-3a; agent under user policy 2026-10-24: a page-to-app
    channel or a relaxed CSP to obtain the host would break the isolation this change exists to prove).
  - The iOS content rule list refuses silently, so the app learns of a refused https request on iOS only through the
    CSP report that the engine sends first; where an engine does not deliver reports the plan is amended before the
    engine's task goes on (design.md D-3a), never shipped without a notice source.
  - A `solo` probe PASS shows a guard suffices against the probe's required cases, not that no case is missing; the
    required-cases list is written from the specs and reviewed, not generated (design.md D-13).
  - On Android, the initial `about:blank` window of an iframe created without `src` runs no document-start script, so a
    peer connection there sends STUN (measured 2026-11-08, `.omp/team-config/evidence/gate/m5-app-design-workspace/probe/android/20261108T215315Z-34233-all/`);
    and Chromium's own preconnect to a host named by a `preconnect` hint reaches the canary's TLS port under every guard,
    about 0.4 s after the hint and again about a second later, which `WebSettings.blockNetworkLoads` does not stop
    (measured 2026-11-08, `experiment-blocknetworkloads-20261108T232024Z-a1fe1-all` on `plan/m5-adw-android`). The engine
    does not contain either; the product app's missing `INTERNET` permission does (task 7.3, `checkNoBackend` on
    the merged `:shellAndroid` manifest), and the probe's Android rows for `rtc-blank` and `net-preconnect` are `accepted`
    (design.md D-8, D-13). Agent under user policy 2026-10-24: no app-side patch reaches either, and dropping the Android
    engine is the disabled-engine path this change does not have. Follow-up (row allocated in `docs/FOLLOW-UPS.md` after
    the merge): the Android shell MUST NOT gain `INTERNET` while the preview is enabled until an engine-level control
    exists for the WebRTC window and for the preconnect.
  - Ten Android probe rows are not shown by a bare run because the probe host or the engine cannot make them leak
    (`perm-clipboard-read`, `perm-motion-sensor`, `perm-fullscreen`, `pop-download-binary`, `pop-file-input`: no user
    activation, no sensor permission exposed, a `text/plain` response; `nav-file`: not a network request; `net-sw`: no
    secure origin; `rtc-datachannel`: no ICE server; `net-css-url`, `net-base-href`: Chromium blocks an http image on an
    https page even with mixed content allowed, Interception's image coverage is `net-img`); three more
    (`perm-geolocation`, `perm-camera`, `perm-microphone`) show the
    request in the result's native map. Every Android guard keeps at least one leaking case, so each has a demonstrated
    negative control (design.md D-13); agent under user policy 2026-10-24: on Android, forcing a user gesture or a
    permission grant into the probe host would measure the host, not the guard (the desktop supplies an activation only to
    get past Chromium's own pop-up blocker and file-chooser check, which hide the guard otherwise, and so that every
    activation-gated case is decided by its guard and not by the race with the 100 ms pulse: on the desktop `perm-fullscreen` leaks
    without its guard once the activation is present, design.md D-13).
  - The probe's desktop title read beyond 4096 characters and its user activation for the activation-gated cases use the in-process
    DevTools protocol client of the JCEF browser, in the probe build only, with no port and no front end (design.md D-13);
    the product's engine builds none.
  - The desktop probe runs with `LocalNetworkAccessChecks` disabled (design.md D-13): Chromium's own check against
    loopback hides the guards from the canary, and the product keeps it as an extra layer never relied on (agent under user
    policy 2026-10-24: a canary off loopback would need a second host address on every developer machine). The guards,
    not that check, are what the probe shows holding.
  - Desktop WebRTC containment of TURN over TCP and over TLS is an engine-level proxy to a closed port whose bypass list
    drops Chromium's implicit loopback bypass, in the product as in the probe, and the desktop `rtc-*` rows are `no-effect`, the constructor staying
    present (design.md D-8; agent under user policy 2026-10-24: the alternative, a constructor-removal script through a
    DevTools client in the product engine, adds a DevTools client the product otherwise has none of, for a second layer the
    measurement shows it does not need).
  - Desktop UDP sockets of an open peer connection: every `RTCPeerConnection` makes the engine's network helper bind two
    unconnected wildcard UDP sockets (`0.0.0.0` and `[::]`, each on an ephemeral port) for as long as the connection lives, with every
    guard on; they gather no candidate and send nothing (the canary stays empty), and no engine setting removes them
    (design.md D-8; cause in `.omp/team-config/evidence/gate/m5-app-design-workspace/f1/diagnosis/desktop-udp.md`).
    The spec "No listening socket" allows exactly these two sockets while the connection is open and none after it is
    closed. How they treat an inbound datagram, which a host on the local network could send to the bound port, is not
    measured: the engine drops it only by inference. Agent under user policy 2026-10-24: nothing in the engine's settings
    removes the sockets and a platform-level control (a firewall or sandbox profile for the helper, a patched engine) is
    beyond a prototype. Follow-up (row allocated in `docs/FOLLOW-UPS.md` after the merge): measure the datagram handling
    of these sockets, and harden at platform level if it is not a drop. The product app on Android and iOS has no such
    socket (no network permission on Android, no UDP on iOS).
  - WebKit's order dependence of the iOS popup observation: on iOS the host's `createWebView` for the probe's scripted
    `target=_blank` click (`pop-target-blank`, the native observation that gives `bare-Popups` its negative control) is only called when
    a synchronous download anchor click ran in the case loop before it (restoring only `pop-download-link` to a synchronous click was enough in 3 of 3 runs); with every download click in a microtask the observation was
    absent in 9 of 9 runs. The probe keeps that order (`gated()` for the five cases, `activated().then` for the three pop-up cases,
    design.md D-13, task 4.16). Why WebKit depends on the order is not diagnosed, and the table is not a proof against the order
    changing with a WebKit update: `ExpectedTableTest` pins the call forms and the iOS `bare-Popups` run fails as `no-negative-control` if
    the observation is lost. A scripted window request under the pop-up guard is not counted on iOS (no `popup` in any iOS `result.json`:
    `javaScriptCanOpenWindowsAutomatically = false` stops it before the UI delegate; the spec "Denied without a prompt" carries this exception), so the guard's path is
    proven only by that leak. Agent under user policy 2026-10-24: reading WebKit to find the cause, and counting a request the host never
    sees, are beyond a prototype; the committed runs show the control and the window never opens. Follow-up (row allocated in `docs/FOLLOW-UPS.md` after the merge): find the WebKit cause, and make the
    observation independent of click order if it can be.
  - On Android the refusal of an off-origin request can only be the app's empty 403 (design.md D-3), so a page-visible
    `no-cors` fetch (`net-fetch-http`, `net-fetch-https`, `own-absolute-other-origin`) may resolve opaque in `solo-Interception`; the probe accepts `blocked` and `opaque-refused` there, and
    `opaque-refused` is not a leak, because the canary logged nothing (agent under user policy 2026-10-24: the engine
    offers no other refusal; which of the two the WebView gives is measured by the Android lane and recorded in the table).
  - The Android probe runs with `mixedContentMode = MIXED_CONTENT_ALWAYS_ALLOW` and the desktop one with
    `LocalNetworkAccessChecks` off (design.md D-13 "Probe-only switches"): the engines' own mixed-content and
    local-network checks hide the guards from the canary; the product keeps both and never relies on them (agent under user
    policy 2026-10-24: an http preview origin would be a different origin than the product's).
  - `Permissions` on iOS has no programmatic negative control: WebKit denies every permission on the custom scheme without
    the guard, so its bare run PASSes and its table pair is listed under `noControl` with that reason (design.md D-13;
    agent under user policy 2026-10-24: forcing a grant into the probe host would measure the host, not the guard). No
    other guard and engine pair is listed.
  - Five iOS probe rows are not shown by a bare run (design.md D-13): `net-prefetch`, `nav-file`, `rtc-datachannel`,
    `pop-download-binary` and `pop-file-input`, because WebKit sends nothing, shows the response (a `.bin` as
    `text/plain`) or gets no activation. Every iOS guard but `Permissions` keeps a leaking case (agent under user policy
    2026-10-24: the form rows leak on a bare iOS run, so the earlier form residual is gone).
  - DNS-only egress (a dns-prefetch hint, any resolver query) is not observed by the probe: the canary has no DNS
    listener and a hint that names an IP literal resolves nothing, so the case `net-dns-prefetch` was removed (agent
    under user policy 2026-10-24). Android is contained by the missing `INTERNET` permission; desktop and iOS stay
    open. Planned follow-up: a DNS listener in the canary (or a probe-controlled resolver) and a dns-prefetch case to a
    name only it resolves (row in `docs/FOLLOW-UPS.md` after the merge).
  - The desktop probe harness has a known weakness: the bare `NavigationVeto` run ended INCONCLUSIVE twice (`the probe
    page produced no result`, `:previewProbe:run` JVM exit 2, 2026-11-09) and passed on both reruns; the cause is not
    found. It cannot turn a leak into a PASS, because an INCONCLUSIVE run is never sealed as evidence; it only costs a
    rerun (agent under user policy 2026-10-24). Planned follow-up: find the cause of the JVM exit (row in
    `docs/FOLLOW-UPS.md` after the merge).
- **Out of scope for blocking**:
  - A minimum content height for the conversation list of a session (every kind, and the Conversation tab of a
    Design session) at large text sizes: it keeps the remainder below the header, the notices and the composer, as since
    `m5-app-shell`; the Preview tab's minimum is task 4.29. Planned follow-up (row in `docs/FOLLOW-UPS.md` after the
    merge).
  - Comment mode, the `pick` bridge and its probe (`m5-app-design-comments`), Present, device widths and zoom
    (`m5-app-design-present`), starting points (FU-267), and the Design extensions of FU-268.
  - The preview route and the encrypted form of page files (ADR-0038 open point 3, M5 server plans).
  - Accessibility of page content inside an engine (a finding for a follow-up, design.md D-10).
  - Windows and Linux desktop engines, and Chromium's own update and component behaviour beyond the switches of D-7.

- [x] 4.22 The fourteenth apply-time amendment, F2 wave 2 blocker W2-B1, cancel during verification or extraction (design.md D-4 "On any failure or cancel it deletes `download.part` and `dir/engine/`" and "A cancel covers the whole attempt"; spec "Progress, cancel and failure"). Defect: `EngineAcquisition.kt` checks cancellation only in `download()`; the install step (cached verification, extraction, the `.weaver-verified` and `install.lock` markers) has no cancel check, so a Cancel during it still commits an installed engine, and `DesktopPreviewEngines.kt` then publishes "The download was cancelled" regardless of the worker's result; `DesignWorkspace.kt` keeps Cancel visible in `Acquiring` throughout. Fix: a Cancel during cached verification or extraction ends the attempt like a Cancel during the download: this attempt's extracted directory and `download.part` are removed (a verified cached archive file is kept), no `.weaver-verified` and no `install.lock` is written, and `Cancelled` is published only after that cleanup. `install` and `installFrom` take the cancel flag; the extractor reads the archive through a stream that ends the attempt once cancel is set, and the cached-archive digest loop checks cancel on every buffer. The cancel is arbitrated against the install commit at one decision point, a single cancel check just before the two markers are written, so either the install commits (the result is the installed engine, whatever arrives after, never the cancelled message) or nothing of it remains; `DesktopPreviewEngines.acquire` publishes the outcome the worker returned, and `NotInstalled("The download was cancelled")` only when the worker never ran. `EngineAcquisition` and `EngineInstaller.create` take an `afterCommit` callback parameter (default: does nothing) that runs once both markers are written, before the outcome is returned, and changes no behaviour (it is a production parameter, so it and the commit-wins test are one commit). Test: `EngineAcquisitionTest` with a barrier-controlled extractor (latch, no sleep): a cancel during the download's extraction and during a cached archive's extraction each ends cancelled with `dir/engine/`, `download.part` and both markers absent; a cancel during a cached archive's verification uses a cancel flag set before the verification starts (the digest loop reads a plain file stream with no injectable reader, and a latch there would need a production read hook nothing else uses), which exercises the per-buffer check on its first iteration, and ends the same way; a cancel after the commit yields the installed result. At the adapter, `DesktopCancelDuringExtractionTest` (`preview/jvmTest`) requires the pane's availability to agree with the disk after a cancel during extraction, and `DesktopCommitWinsTest.aCancelAfterTheCommitAndBeforeTheOutcomeIsPublishedLeavesReadyAndTheInstallOnDisk` (in `DesktopAvailabilityTest.kt`) parks the worker in `afterCommit`, cancels `acquire`, releases the worker and requires `Availability.Ready` and the committed installation on disk; its RED is recorded from a scratch copy of the pre-fix adapter (it expected `Ready` and got `NotInstalled` with the reason "The download was cancelled", `red/red-f2-4.22-b.txt`). Verify: `(cd app && env -u DEBUG ./gradlew :previewAcquire:jvmTest :preview:jvmTest)`
