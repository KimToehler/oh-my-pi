## Findings

### F1-check-then-insert-race
- **Disposition**: adopted: design.md D1 now reserves inside one transaction on a `pool.connect()` client that locks the event row with `SELECT capacity ... FOR UPDATE` before a separate count and the insert, states why lock and count stay separate statements, adds a Build vs. adopt subsection, and design.md Risks plus gate.md Accepted residual risks name the lock-wait cost

### F2-contested-seat-proof-contradicts-D1-and-cannot-discriminate
- **Disposition**: adopted: tasks.md 2.1 now tests a 20-call `Promise.all` burst at capacity 1 and 3 asserting exactly `capacity` successes and rows, with its failing run against a check-then-insert version kept as `burst-red.txt`; task 3.1's `last-seat-contested` row is a 20-curl burst split across both instances

### F3-reserveSeat-contract-cannot-produce-the-404
- **Disposition**: adopted: design.md D1 gives `reserveSeat` three outcomes (row, `"full"`, `"not_found"` from the locked select), D3 maps them to 201, 409 and 404 with no further query and answers 400 for a body that is not valid JSON, and tasks.md 2.2 tests the invalid-JSON 400

### F4-repeat-reservations-by-one-user-undecided
- **Disposition**: adopted: design.md Non-Goals states that each request reserves one seat, a repeated request by the same user reserves another, and D2 deliberately has no `UNIQUE (event_id, user_id)`
