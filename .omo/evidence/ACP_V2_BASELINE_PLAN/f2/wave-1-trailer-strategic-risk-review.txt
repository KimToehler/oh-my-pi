**Bottom line:** The two-surface architecture is sound overall: version negotiation stays in `AgentSideConnection`, protocol-specific behavior stays behind `AcpSurface`, and persistence remains owned by `AgentSession`. The review fails on one temporal race: cancellation or close can emit terminal `idle(cancelled)` while an already-running event handler still has another update to send.

Blocker B1: class: `terminal-transition-overtakes-inflight-update`. Trigger: the user presses Stop, or closes the session, while `AcpAgent.#handlePromptEvent` is between two notifications produced by one ordinary event—for example, a completed `todo` tool maps to `tool_call_update` followed by `plan_update`; client backpressure makes this a realistic window. Preconditions: an active v2 foreground and an event handler that has sent its first mapped update but is awaiting its write. Impact: `AcpAgent.#beginCancelCleanup` immediately calls `#finishPrompt`, and `AcpSurfaceV2.onForegroundEnd` queues `idle(cancelled)` without awaiting `record.promptEventHandlers`; the handler can then queue its second update after that idle, so idle is not the terminal frame and Air can render activity after declaring the run stopped. This breaks the foreground-closure and cancellation criteria and the QA contract that nothing follows terminal idle. Damage is reversible through a subsequent turn or reopen, but it directly breaks the feature goal. sites: whole-tree search for `waitForUpdateDeliveries\(|#beginCancelCleanup\(|onForegroundEnd\(|sendMapped\(|mapAgentSessionEventToAcpV2Updates\(` under `packages/` found the causal production sites `packages/coding-agent/src/modes/acp/acp-agent.ts::{#handlePromptEvent,#waitForUpdateDeliveries,#beginCancelCleanup}`, `packages/coding-agent/src/modes/acp/acp-event-mapper.ts::mapAgentSessionEventToAcpSessionUpdates` (`tool_execution_end`), `packages/coding-agent/src/modes/acp/acp-event-mapper-v2.ts::mapAgentSessionEventToAcpV2Updates`, and `packages/coding-agent/src/modes/acp/acp-surface-v2.ts::{onForegroundEnd,#emitState,sendMapped}`. The search found no call that uses the existing `waitForUpdateDeliveries` host operation to guard cancellation terminalization.

### 1. Does the change hold up architecturally?

Apart from B1, yes. `packages/utils/src/acp/connection.ts::AgentSideConnection` fixes the negotiated version for the connection; `packages/coding-agent/src/modes/acp/acp-surface.ts::AcpSurface` gives v1 and v2 separate lifecycle and mapping policies; and `packages/coding-agent/src/session/agent-session.ts::{#registerSubmission,#settleSubmission,#dropSubmission,settlePendingSubmissions}` keeps insertion identity and tombstoning in the persistence owner. The default-off `cfgAcpProtocolV2` also contains draft-protocol risk without contaminating v1.

Note: `AgentSideConnection.#dispatch` accepts stateful v1 requests before initialization, while `AcpAgent.#registerPreparedSession` installs `record.surfaceUnsubscribe` only for the surface active at registration. A client that deliberately creates a session before initialize and later negotiates v2 can therefore retain a record without v2’s lifetime subscription. This does not block because it requires deliberately misordering the local ACP handshake and is recoverable, but rejecting pre-initialize stateful methods would make the architecture stricter.

### 2. What does the auditor’s line-level view structurally miss?

It misses the ordering created by composition across four individually plausible mechanisms: asynchronous session-event handlers, events that map to multiple notifications, transport-level serialized writes, and synchronous cancellation terminalization. The unused `AcpSurfaceHost.waitForUpdateDeliveries` operation is the architectural signal that this barrier was anticipated but not connected to `#beginCancelCleanup` or close.

### 3. Which production failure would hurt most, and is it addressed?

The highest-consequence failure would be acknowledging a prompt that was never persisted: the client would treat the message as committed while the model and replay history never contained it. That is well addressed by the persisted entry-id callback, tombstones, replay stamping, and the real-session identity tests.

The highest remaining risk is lifecycle desynchronization after Stop. Autonomous wake framing and ordinary foreground completion are covered, but B1 leaves a normal cancellation race in which updates can follow terminal idle.

### 4. Is any auditor finding a false positive on unchanged behavior?

No. The auditor’s batch-context note concerns newly introduced transport behavior and is correctly non-blocking because the only new consumer rejects batched prompts before admission.

However, the auditor’s `security_delta: no` is a false negative under the supplied definition, not a false-positive finding: `AcpAgent.v2Handler.login/logout` and `AcpSurfaceV2.authMethods` add an authentication/logout wire path around shared provider credentials. No credential mutation or exploit is substantiated, so this is metadata classification rather than another implementation blocker.

### Action plan

1. Split cancellation into “mark cancelled and abort” and “emit terminal state”; after marking `work.cancelRequested`, await the snapshot of `record.promptEventHandlers` before v2 emits `idle(cancelled)`.
2. During close, keep the record available to the ordered send path until that delivery barrier completes; remove it from `#sessions` only once no accepted handler can enqueue another update.
3. Add a committed v2 boundary regression that delays the first update of a two-update `todo` completion, issues `session/cancel`, then releases delivery and asserts `tool_call_update`, `plan_update`, and finally `idle(cancelled)`, with no later session update.
4. Add the equivalent close assertion or parameterize the same probe for Stop and close.
5. Preserve v1 golden bytes and rerun the focused ACP, transport, and agent-session suites plus the scripted cancel QA after the fix.

**Effort:** Short (1–4h).

**Confidence:** High. The failing order follows directly from the awaited per-notification loop in `#handlePromptEvent`, the synchronous `#finishPrompt` call in `#beginCancelCleanup`, and the absence of any cancellation call to `waitForUpdateDeliveries`.

**Watch out for:**
- Do not wait on the current `agent_end` handler from inside itself; the barrier belongs to external cancel/close paths.
- Moving record deletion must still set `closedError` synchronously so no new work is admitted during teardown.
- Keep the fix v2-specific where necessary so v1 prompt-settlement bytes remain unchanged.
